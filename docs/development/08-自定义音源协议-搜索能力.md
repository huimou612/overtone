# 08 自定义音源协议 —— 搜索能力

> 状态：已完成 · 2026-10-15
> 上游对照：LX Music 的自定义源协议（`lx.send` / `lx.on` / `lx.request`）保持不变，
> 只是把「允许声明哪些能力」的白名单放宽，并补上搜索结果的校验与规范化。

## 1. 为什么要做

上一轮把内置平台接口整体删掉之后（见 [07-开放曲库-音源方案](./07-开放曲库-音源方案.md)），
应用只剩两条能出声的路：开放曲库、以及**用户自己导入的自定义源**。

但自定义源协议那时只放行一种能力 —— `musicUrl`（取播放地址）。这是照着 LX Music 的
分工来的：LX 有内置接口负责搜索、榜单、歌单、歌词、封面，自定义源只补「取地址」。
它这套分工的前提是**内置接口存在**。泛音把内置接口删了，于是：

| 用户导入一个自定义源之后 | 结果 |
|---|---|
| 搜索页 | 只有「开放曲库」和「聚合搜索」两栏，**没有这个源** |
| 搜到的歌 | 没有（因为压根搜不了） |
| 歌词 | 没有 |
| 封面 | 没有 |

也就是说：**用户手里的源其实只能"放"，没法"找"** —— 而且连"放"都很难走到，
因为没有任何入口能搜出属于这个源的歌。这就是本轮要补的缺口。

## 2. 协议扩展：从「一种能力」到「四种」

改动集中在 `main/modules/userApi/renderer/preload.js` 的两张白名单：

```js
// 能力白名单：脚本声明什么、由这里过滤
const supportActions = {
  kw: ['musicUrl', 'musicSearch', 'lyric', 'pic'],
  kg: ['musicUrl', 'musicSearch', 'lyric', 'pic'],
  tx: ['musicUrl', 'musicSearch', 'lyric', 'pic'],
  wy: ['musicUrl', 'musicSearch', 'lyric', 'pic'],
  mg: ['musicUrl', 'musicSearch', 'lyric', 'pic'],
  xm: ['musicUrl'],
  local: ['musicUrl', 'lyric', 'pic'],
}
```

新增三个：`musicSearch`（搜索）、`lyric`（歌词）、`pic`（封面）。
后两个跟搜索是同一个病因 —— 内置接口没了，它们也没有提供者，一起补上。

### 不做的事

- **不允许脚本造新的 source id。** `allSources` 仍是
  `['kw','kg','tx','wy','mg','local']`。原因：源名来自语言包（`source_kw` = 酷我音乐），
  新增 id 就得再做一套动态命名体系，而收益只是"可以自己起名"。LX 生态的脚本本来就是
  围着这几个 id 写的。
- **静默丢弃白名单之外的能力。** 脚本声明了不认的能力不会报错，只会被过滤掉。
  这是上游行为，保留了 —— 但**排错时要先想到这里**，而不是盯着自己的代码。

## 3. 脚本侧契约

### 3.1 声明能力

```js
lx.send(lx.EVENT_NAMES.inited, {
  sources: {
    kw: {
      type: 'music',
      actions: ['musicUrl', 'musicSearch', 'lyric', 'pic'],
      qualitys: ['128k'],
    },
  },
})
```

### 3.2 响应请求

```js
// ⚠️ handler 必须返回 Promise —— 宿主那边是 `events.request.call(...).then(...)`，
//    返回普通值会直接 TypeError: .then is not a function（被 try/catch 吞成一条失败响应）
lx.on(lx.EVENT_NAMES.request, async ({ source, action, info }) => {
  switch (action) {
    case 'musicSearch':
      // info = { text, page, limit }
      return { list, total: 3 }        // limit / allPage 可省，宿主会补齐
    case 'musicUrl':
      return 'https://.../x.mp3'       // 必须是 http(s)，长度 ≤ 2048
    case 'lyric':
      return { lyric: '...', tlyric: null, rlyric: null, lxlyric: null }
    case 'pic':
      return 'https://.../cover.jpg'
  }
})
```

### 3.3 搜索结果的结构契约

```js
{
  list: [
    {
      name: '歌名',            // 必填
      songmid: 'abc',         // 必填（别名：songId / id，三个都认）
      singer: '歌手',          // 别名：artist
      albumName: '专辑',       // 别名：album
      interval: 129000,       // 秒数 / 毫秒 / '02:09' 都接受，宿主统一归一化成 mm:ss
      img: 'https://...',     // 别名：pic
    },
  ],
  total: 240,                 // 可省，默认 list.length
  limit: 20,                  // 可省，默认 info.limit（夹紧到 [1, 100]）
  allPage: 12,                // 可省，默认 ceil(total / limit)
}
```

也允许**直接返回裸数组**，等价于 `{ list }`。

### 3.4 三条硬约束

1. **必须同一个源同时提供 `musicSearch` 和 `musicUrl`。**
   搜出来的歌 `source` 就是脚本声明的那个源，取播放地址也要走它
   （`core/music/utils.ts` 的 `musicSdk[source].getMusicUrl`）。
   声明了搜索却没有取地址能力 = 给用户一个必然失败的入口。
   宿主**主动拦掉**这种情况并打一条 warn（见 §5 的第 3 点），而不是让用户去撞。
2. **`name` 与 `songmid` 必填。** 前者要显示与排序，后者要拼歌曲 id
   （`toNewMusicInfo` 生成 `${source}_${songmid}`，`deduplicationList` 靠它去重）。
   缺一个整条结果作废（抛错 → 渲染层看到「搜索失败」）。
3. **`source` 由宿主钉死。** 脚本给了也不采信 —— 它决定这首歌走哪条播放路径，
   乱标的后果是取到别人的实现。

### 3.5 规模限制

- 单页最多 **100 条**（超出直接截断）。
- 整份结果 JSON 最长 **1 MB** —— 结果要从「沙箱窗口 → 主进程 → 渲染进程」连传两趟，
  塞个几 MB 会把 IPC 卡住。

## 4. 宿主侧：新增一个可搜索的源要动哪几处

| # | 位置 | 做什么 |
|---|---|---|
| 1 | `main/modules/userApi/renderer/preload.js` | `supportActions` 放开能力；`handleRequest` 加 `musicSearch` 分支 |
| 2 | `main/modules/userApi/renderer/preload.js` | `verifySearchResult` / `normalizeMusicItem` / `normalizeInterval` 做校验与规范化 |
| 3 | `common/types/user_api.d.ts` | `UserApiSourceInfoActions` 加 `musicSearch`；补 `UserApiSearchItem` / `UserApiSearchResult` |
| 4 | `renderer/core/useApp/useInitUserApi.ts` | `case 'musicSearch'` 构造实现；**结尾调 `initSearchSources(...)`** |
| 5 | `renderer/store/search/music/state.ts` | `sources` 改成可重建（`initSearchSources`） |
| 6 | `renderer/views/Search/index.vue` | Tab 列表由一次性 `map` 改成 `computed` |

⚠️ **第 5、6 处是这次最容易漏的地方**，因为它们不是"新功能"，而是**旧假设被打破**：

`store/search/music/state.ts` 原来在**模块加载时**一次性建好 `sources` 数组（`markRaw([])`），
因为那时候源是编译期就确定的（内置平台）。而自定义源是**运行时异步注册**的
（主进程把脚本跑起来、把声明回传之后 `userApi.apis` 才有内容）。
`markRaw` 的数组 push 不触发任何重渲染 → 表现为「源都加载好了，Tab 就是不出现」。
同理 `Search/index.vue` 里 `_sources.map(...)` 是一次性快照，必须改成 `computed`。

### 判据不能写成 `musicSdk[id]?.musicSearch`

`musicSdk` 是个 Proxy，取**任何** key（包括 `kw`/`kg`）都会兜到空壳上，
而空壳**也有** `musicSearch`（返回空结果）。用它当"这个源可搜吗"的判据，
kw/kg/tx/wy/mg 会无条件冒出来，变成一排「点进去什么都搜不到」的死 Tab。

正确判据只有两个来源：
- 内置源 → 看 `music.sources`（现在只有 `ov`）；
- 自定义源 → 看 `userApi.apis[id].musicSearch` 是否存在，
  而这个汇总只有 `useInitUserApi` 做得了，所以由它把 id 列表**传参**给 `initSearchSources`。

## 5. 顺带修掉的三处

1. **在线源的 `getPic` 形状不匹配（真实缺陷，本轮暴露）。**
   `core/music/utils.ts` 对 `getPic` 有**两种消费形状**：
   - `local`：`apis('local').getPic(...).promise`（:211）
   - 在线源：`musicSdk[source].getPic(...)`，返回值**直接被当 Promise 用**（:363 / :393）

   上游只给 `local` 实现了 pic，所以在线源这条形状从没被验证过。
   放开了自定义源的 `pic` 能力之后，第一次调用就报 `reqPromise.then is not a function`。
   现在按 source 分开返回：`local` 包 `{ canceleFn, promise }`，其余直接返回 Promise。

2. **`store/search/*/action.ts` 里 `listInfo` 的兜底。**
   路由上的 `source` 与 `listInfos` 不同步时（刚切完自定义源、旧链接），
   `listInfos[sourceId]` 是 undefined，紧接着就往它上面写 `.key` / `.noItemLabel` → TypeError。
   统一改成 `?? listInfos.all`（聚合视图始终存在）。
   歌单分栏尤其需要：它的源列表**不含**自定义源，但搜索页的 Tab 是「歌曲」分栏的，
   所以在歌单分栏下 `source=kw` 是正常状态。

3. **「搜得到必须播得了」的一致性守卫。**
   声明了 `musicSearch` 但没有 `musicUrl` 的源，宿主**跳过搜索注册**并 warn：

   ```
   [userApi]「kg」声明了 musicSearch 但没有 musicUrl，已跳过搜索注册：搜出来的歌取不到播放地址
   ```

   理由和上一轮 `assertApiSupport` 那次一样：一个点了没反应的入口，比压根没有入口更糟。

## 7. 踩过的坑

1. **`document.hidden` 与虚拟列表。** 与 [07](./07-开放曲库-音源方案.md) 同一条：
   窗口被盖住时 Chromium 不跑 `requestAnimationFrame`，虚拟列表算出总高却渲染 0 行。
   **截图要排在读 DOM 之前**（`Page.captureScreenshot` 会强制出一帧）。

2. **webpack-dev-server 的 overlay 是个全屏 `<iframe>`。**
   `#webpack-dev-server-client-overlay`，`position: fixed; inset: 0; z-index: 2147483647`。
   两个后果：① 有内容时画面变暗（**很像深色主题生效**）；
   ② **它创建过就一直存在** —— HMR 修好之后内容清了、元素还留着（实测 `outerHTML` 是个
   空的 `about:blank`），所以判据必须是"里面有没有内容"，空壳直接 `remove()`。
   它**不只**显示编译错误，也显示**运行时未捕获错误**（本机常驻一条：
   `ov` 连不上 `api.openverse.org`，聚合搜索里那条 rejection 没人接住）。

3. **`python -m http.server` 不支持 Range 请求** → 一律返回 200 + 全量 body。
   而 Chromium 的媒体栈要靠 206 分段响应来探测/seek，拿不到就报
   `DEMUXER_ERROR_COULD_NOT_OPEN: FFmpegDemuxer: open context failed`，
   **看起来像音频文件坏了**。同一个 mp3 换成支持 Range 的服务后立刻正常（duration 3s）。
   验证音频可达性时一定要用 `.git/serve-media.py` 这种带 Range 的服务。

4. **`process.argv.find(a => !a.startsWith('--'))` 取到的是 `node.exe` 的路径。**
   必须 `slice(2)`。

5. **`try { const x } finally { x }` 看不见** —— 块级作用域。
   要在 `finally` 里汇总的东西得声明在 `try` 外面。

6. **`finally` 里的 `process.exit()` 会吞掉异常。** 验证脚本里某个段落抛错、
   直接走 `finally` 的 `process.exit(0)`，退出码会是 0、异常无声消失。
   段落内部要自己兜底（返回 error 对象）而不是让它抛出去。

7. **`dist/user-api-preload.js` 是 webpack 产物**（入口见
   `build-config/renderer-scripts/webpack.config.base.js`，输出到 `dist/`）。
   改了 `preload.js` 必须等重新编译、**并且重启 Electron** ——
   沙箱窗口是在 app 启动时创建并加载 preload 的，光有产物更新不生效。
   症状：`userApi.apis.kw` 只有 `getMusicUrl`，看起来像白名单没放开。
