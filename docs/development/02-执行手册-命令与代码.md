## 1. 环境变量（每次开新终端都要设）

**⚠️ 这是本机最容易踩的坑**：npm registry 已经指向淘宝镜像，但 **Electron 二进制镜像没有配**。
不设这个，`npm i` 会卡在下载 Electron（100 MB+，从 GitHub 拉）上，慢到不可接受。

```bash
export ELECTRON_MIRROR="https://npmmirror.com/mirrors/electron/"
export ELECTRON_BUILDER_BINARIES_MIRROR="https://npmmirror.com/mirrors/electron-builder-binaries/"
export SASS_BINARY_SITE="https://npmmirror.com/mirrors/node-sass"
```

**不要用** LX 源码里的 `npm run up` / `npm run dp` —— 它们硬编码了作者自己的代理 `127.0.0.1:2081`，本机没开这个端口。

## 2. 阶段 1：让 LX 外壳跑起来

### 2.1 安装依赖

```bash
cd F:/workbuddy/2026-10-12-13-28-07/fusion-music/app

export ELECTRON_MIRROR="https://npmmirror.com/mirrors/electron/"

"C:/Users/HP/.workbuddy/binaries/node/versions/22.22.2-6/node.exe" \
  "C:/Users/HP/.workbuddy/binaries/node/versions/22.22.2-6/node_modules/npm/bin/npm-cli.js" \
  install --no-audit --no-fund
```

**为什么用 `node npm-cli.js` 而不是直接 `npm`**：本机 bash 环境下 npm/npx 的 Windows shim 偶发失效（报「不是内部或外部命令」）。用 node 直接跑入口脚本最稳。

预计：约 1.5–2 GB 的 `node_modules`，首次安装 10–20 分钟。

### 2.2 启动开发模式

```bash
npm run dev
```

`dev` 脚本实际执行：`cross-env NODE_OPTIONS=--max-http-header-size=200000 node build-config/runner-dev.js`

它会：
1. 用 webpack 编译 main / renderer / renderer-lyric 三个入口
2. 启动 webpack-dev-server（带热重载）
3. 拉起 Electron 主进程

改 `src/renderer/` 下的文件会热更新；改 `src/main/` 下的需要重启。

### 2.3 完整构建

```bash
npm run build          # = node build-config/pack.js，跑全部 4 个 webpack 配置
```

也可以单独构建某一层：

```bash
npm run build:main              # 主进程
npm run build:renderer          # 主 UI 窗口
npm run build:renderer-lyric    # 桌面歌词窗口
npm run build:renderer-scripts  # 注入脚本
```

### 2.4 打 Windows 绿色包

```bash
npm run pack:win:7z:x64
```

产物在 `publish/` 或 `build/` 下（由 `build-config/build-pack.js` 决定）。

其他目标：
```bash
npm run pack:win:setup:x64     # NSIS 安装包
npm run pack:win:portable:x64  # 便携版
npm run pack:dir               # 只出解包目录（调试用，最快）
```

## 3. 加一个新能力的标准动作（三步）

以「AI 音源分离」为例。**这是缝合的核心操作范式，后面每加一个功能都照这个来。**

### 第 1 步：在 IPC 契约里注册（`src/common/ipcNames.ts`）

找到 `const modules = {` 里的 `winMain:` 之后，插入新模块：

```ts
  ai: {
    separate_stems: 'separate_stems',
    separate_cancel: 'separate_cancel',
    separate_progress: 'separate_progress',
    generate_lyric: 'generate_lyric',
    get_models: 'get_models',
    download_model: 'download_model',
    set_ai_credential: 'set_ai_credential',
    get_ai_status: 'get_ai_status',
  },
```

然后文件底部照现有写法导出：

```ts
export const AI_EVENT_NAME = modules.ai
```

命名规则：`${模块名}_${事件名}` → 自动拼成 `ai_separate_stems`。

**为什么第一步是这个**：这个文件是主进程与渲染层之间**唯一的契约来源**。先定契约，两边才能各写各的。

### 第 2 步：写主进程模块（`src/main/modules/ai/`）

新建 `src/main/modules/ai/index.ts`，骨架：

```ts
import { AI_EVENT_NAME } from '@common/ipcNames'
import { onMainIpc } from '@/utils/ipc'   // 按项目实际工具函数调整
import { separateStems } from './analysis'

export default () => {
  // 音源分离
  onMainIpc(AI_EVENT_NAME.separate_stems, async (event, musicInfo, options) => {
    return separateStems(musicInfo, options, (progress) => {
      event.sender.send(AI_EVENT_NAME.separate_progress, progress)
    })
  })

  onMainIpc(AI_EVENT_NAME.separate_cancel, (event, taskId) => {
    // 取消逻辑
  })
}
```

再把从 Folia 搬来的 `.cjs` 文件放到 `src/main/modules/ai/analysis/`，在 `index.ts` 里 require 进来。

**注意**：Folia 的 `electron/analysis/*` 是 `.cjs`（纯 CommonJS），LX 主进程是 TS 编译成 CJS。接入方式：
- 方案一：`.cjs` 原样放着，TS 里用 `require()` 引（`esModuleInterop` 下最省事）
- 方案二：改写成 `.ts`，加上类型（工作量大但更干净）

建议先方案一，跑通后再逐步方案二。

### 第 3 步：写 Vue 界面（`src/renderer/`）

1. 新建 `src/renderer/views/AI/Separate.vue`
2. 在 `src/renderer/router.ts` 挂路由
3. 在 `src/renderer/components/layout/` 的侧边栏加入口

调用方式（按 LX 现有写法）：

```ts
import { AI_EVENT_NAME } from '@common/ipcNames'
// 主进程 → 渲染层用 window.lx 或项目封装好的 api，参照 views/Setting 里的用法
```

**先照抄 `src/renderer/views/Setting/` 的结构**——那里有 37 个文件，是最完整的「多页签设置界面」范例，新页面照着它的目录组织和样式类名写，视觉上就统一了。

## 8. 推送到 GitHub：完整可用流程（2026-10-12 实测）

### 8.1 建仓库：连接器无权限时，复用 git 凭据里的 token

GitHub 连接器只有只读权限，建仓会报 `403 Resource not accessible by integration`。
本机 git 凭据管理器（GCM）里存着一把带 `repo` 权限的 OAuth token，直接取来用：

```bash
cd <repo>
export GIT_TERMINAL_PROMPT=0
printf 'protocol=https\nhost=github.com\n\n' | git credential fill
# 输出里 username=... / password=gho_xxxxxxxx  ← 这就是 token

TOKEN=gho_xxxxxxxx
curl.exe -s -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -H "Accept: application/vnd.github+json" \
  -d '{"name":"overtone","description":"...","private":true,"auto_init":false}' \
  https://api.github.com/user/repos
```

查 token 权限范围：`curl.exe -s -D - -o /dev/null -H "Authorization: Bearer $TOKEN" https://api.github.com/user | grep -i x-oauth-scopes`
本项目实测为 `gist, repo, workflow`——`repo` 即可建私有库。

⚠️ 建仓时**不要**勾 `auto_init` / README / .gitignore / LICENSE，保持完全空仓库，否则推送时要先 pull 合并。

### 8.2 分支名必须是 `master`，不能是 `main`

`src/renderer/utils/update.js` 里的版本检查地址写死了 `/master/publish/version.json`。
分支叫 `main` 会让自动更新功能永久失效。重命名：

```bash
git branch -M fusion master     # local master 只是上游 v2.12.6 指针，是 fusion 的祖先，覆盖不丢提交
git push -u origin master
```

### 8.3 ⚠️ 最大的坑：浅克隆推不到新建的空仓库

**症状**：
```
remote: fatal: did not receive expected object a04cf3b3071b0878264019f19d7a0cbc68364db8
error: remote unpack failed: index-pack failed
! [remote rejected] master -> master (failed)
```

**根因**：本地是 `--depth=1` 浅克隆，`.git/shallow` 里只有一个嫁接点。
推送时 git 发包只包含「远端没有的对象」，它认为远端有嫁接点之前的祖先；
但新建的空仓库什么都没有，服务端 `index-pack` 索要完整祖先闭包 → 拿不到 → 失败。

**判定**：`git rev-parse --is-shallow-repository` → `true` 就一定会踩。

**修复**：补全历史。本机两种方式：

| 方式 | 结果 |
|---|---|
| `git fetch --unshallow upstream`（直连 GitHub） | ❌ `schannel: server closed abruptly (missing close_notify)` |
| 同上但加 `-c http.version=HTTP/1.1` | ❌ 仍然中断 |
| `git fetch --unshallow mirror`（gitee 镜像） | ⚠️ exit=0 但仍是 shallow（镜像 master 不含嫁接点祖先） |
| 同上（gitcode 镜像） | ⚠️ 同上 |
| **`https://ghproxy.net/https://github.com/...`** | ✅ **成功，2594 提交，回溯到 2019-08-14 Initial commit** |

一键脚本：`bash build-config/fetch-full-history.sh`（依次尝试 gitee → gitcode → ghproxy.net，失败自动退化为 `--deepen` 分块推进）。

**镜像可达性实测**（`notes/probe_mirrors.py`）：

| 源 | 结果 |
|---|---|
| `gitee.com/mirrors/lx-music-desktop` | ✅ 1.3–1.8s（但历史不完整） |
| `gitcode.com/gh_mirrors/lx/lx-music-desktop` | ✅ 1.5s（同上） |
| `ghproxy.net/https://github.com/...` | ✅ 3.2s **且历史完整** |
| `gh-proxy.com/https://github.com/...` | ✅ 2.3s |
| `kkgithub.com` | ❌ schannel 证书校验失败 |
| `ghfast.top` | ❌ CONNECT tunnel 502 |
| `gitclone.com` | ❌ URL 被拒 |
| `github.com` 直连 | ❌ 连接超时 |

### 8.4 推送：两个坑叠在一起，现在用脚本一次绕开

> **2026-10-13 修正。** 本节此前写的是「推送实测约 20 分钟、看不到进度不要以为卡死」——
> 那个结论**是错的**，把两个真实故障当成了「正常慢」。一次真实事故：push 卡满 **37 分钟**、
> 8 次重试全部失败、日志**一个字节都没有**。

**坑 1：直连 github.com 不通。** 环境里没有 `HTTP_PROXY` / `HTTPS_PROXY` 变量，git 默认直连就撞墙：

```bash
curl https://github.com                            # → 000，20s 超时
curl -x http://127.0.0.1:7897 https://github.com   # → 200，1.7s
```

本机代理是 **clash-verge**（核心进程 `verge-mihomo`），混合端口 **7897**（7898 / 7899 也在听）。
上游 LX 脚本里写的 `127.0.0.1:2081` 是作者自己的配置，**本机没有这个端口**。
报错有两种形态，都指向「连不上」而不是「慢」：

```
Failed to connect to github.com:443 after 21073 ms: Could not connect to server
Recv failure: Connection was reset
```

**坑 2：凭据助手是 GUI 弹窗选择器，会把 git 挂死。** PortableGit 的 **system 级**
gitconfig 硬配了 `credential.helper = helper-selector`。它是弹窗式选择器，没人点就永久等待；
而 `credential.helper` 是**累积列表** —— system 级排最前，永远轮不到 global 级那个真正能用的
`git-credential-manager`。**`GIT_TERMINAL_PROMPT=0` 拦不住它**（那个变量管终端提示，不管 GUI 弹窗）。
`GIT_TRACE=1` 里能看到它停在 `git credential-helper-selector get`。
注意：**删 repo 级配置没用，它在 system 级。**

**现在的用法 —— 直接跑脚本，两层都绕开：**

```bash
bash build-config/push-retry.sh
```

脚本做的事：探测可用代理 → 从凭据管理器取 token（`read-gh-token.py`，Win32 `CredRead`，
只写 `.git/ghtoken`，`trap` 保证退出即删）→ 用 `-c credential.helper=`（空值清空整个 helper 列表）
+ 凭据放进 URL → 推送 → 补一次 `fetch` 同步 remote-tracking。

正常输出长这样（实测一次通过，几秒）：

```
探测到可用代理 http://127.0.0.1:7897
FOUND user=huimou612 length=40 preview=gho_…t1
=== push attempt 1/4  15:02:14 ===
To https://github.com/huimou612/overtone.git
   e7b5d4a3..8319de9e  master -> master
PUSH_OK
```

**排查时记住两条：**

1. **长任务别用 `cmd | tail` 包装。** 输出会被完全缓冲，进程不结束就一个字都看不到 ——
   37 分钟里日志为空就是这么来的。改成 `> file.log 2>&1` 再单独读文件。
2. **卡住时上 `GIT_TRACE=1`。** 它直接告诉你是卡在代理、卡在凭据，还是卡在传数据。
3. 顺带一个环境限制：**PowerShell 的 `Add-Type`（运行时编译 .NET）被本机安全策略拦截**，
   要读凭据管理器就用 Python `ctypes`（`read-gh-token.py` 就是这么写的）。

## 9. LX 逐字歌词格式 `lxlrc`（阶段 3 的产出目标）

**重要发现：LX 本身就内置逐字歌词渲染，不用重造轮子。**

- 设置项：`player.isPlayLxlrc`（播放逐字歌词）、`player.isShowLyricRoma`、`player.isShowLyricTranslation`
- 数据字段：`musicInfo.lxlrc`
- 渲染入口：`src/renderer/core/lyric.ts` → `lrc.setLyric(appSetting['player.isPlayLxlrc'] && musicInfo.lxlrc ? musicInfo.lxlrc : musicInfo.lrc, ...)`
- 类型定义：`src/common/types/music.d.ts`、`player.d.ts`、`desktop_lyric.d.ts`

**格式**（从 `src/common/utils/lyricUtils/kg.js` 反推，酷狗 KRC 解密后就转成它）：

```
[mm:ss.mmm]<起始毫秒,时长毫秒>字<起始毫秒,时长毫秒>字<起始毫秒,时长毫秒>字
```

- 行首 `[mm:ss.mmm]` 是该行起始时间
- 行内每个 `<offset,duration>` 紧跟一个字符/词
- 纯文本 lrc = 把 `<...>` 全部删掉：`lxlyric.replace(/<\d+,\d+>/g, '')`

> ⚠️ **两个字段名不要混**（2026-10-12 落地时确认）：
> - `musicInfo.lxlrc` —— 音源 SDK 层返回的字段
> - `LX.Music.LyricInfo.lxlyric` —— 歌词存储层（`lyrics` 表 + dbService）的字段
>
> 两者之间由 `LyricPlayer.vue:111` 的 `lyricInfo.lxlyric = playerMusicInfo.lxlrc` 搭桥。
> **写回歌词要走 `lxlyric`**（通过 `dbService.editedLyricUpdateAddAndUpdate`），
> 不是 `lxlrc`。

**对阶段 3 的意义**：AI 分词的产物只要拼成这个字符串写进歌词信息，就能直接被现有
渲染链路消费（主窗口 + 桌面歌词窗口都会生效），**无需改渲染层**。
`boundaries`（每行的分词边界）→ lxlrc 的转换器是阶段 3 的主要工作量。

> ⚠️ **这个格式远比上面三行复杂，有几条不满足就会「不报错但功能没了」。**

## 10. CI 的结构（改之前先读，别把竞态改回来）

`.github/workflows/release.yml` 是**两阶段**结构，不是「每个平台各自发布」：

```
Windows ─┐
Windows_7├─ 各自 npm run build + npm run pack:*（publish=never）
Mac      │  → actions/upload-artifact
Linux   ─┘
              ↓ needs
        Release ── download-artifact(merge-multiple)
                  → 清理同 tag 的历史草稿与残留 tag
                  → gh release create --draft   ← 只此一处创建 Release
```

**为什么不能回到 `publish:*`：** `publish:*` 对应 `publish=always`，electron-builder 的
GitHub publisher 会去创建 draft release。**draft 不占 git tag**，所以四个并行的 job
互相查不到对方，会各自建一个同名草稿。实测一次推送留下 2 份 `v0.1.0`、合计 1.5 GB
重复安装包，而且每推一次就继续增长。

改动时请守住这三条：

1. **`pack:*` 而不是 `publish:*`**（`build-pack.js` 里 `publish` 默认 `'never'`）
2. **创建 Release 的地方有且只有 `Release` job 一处**
3. **`Release` 必须 `needs` 四个平台**，否则会在产物不全时就发布

改完必须验证：

```bash
# YAML 结构 + 24 个 run: 块的 shell 语法 + npm run 目标是否存在 + 无 publish:* 残留
C:/Users/HP/.workbuddy/binaries/python/envs/default/Scripts/python.exe build-config/validate-workflow.py
```

> 本机坑：`bash -n` 里的 `bash` 会解析到 **WSL 的 bash**，被安全策略拦截后
> 每个块都报「语法失败」（假象）。必须用 Git Bash 的绝对路径，脚本里已处理。

`concurrency` 开了 `cancel-in-progress`：同一分支上后一次推送会取消前一次未完成的构建。
这是安全的 —— 取消发生在打包中途，`Release` 是流水线最后一步，不会留下半成品草稿。

## 12. AI 歌词功能：怎么用、怎么加界面

IPC 契约（`AI_EVENT_NAME`，共 10 个）：

| 事件 | 参数 | 返回 |
|---|---|---|
| `ai_get_status` | — | `{provider, encrypted, credentials, settings, limits}` |
| `ai_set_setting` | `{key, value}` | 白名单：AI_PROVIDER、OPENAI_API_URL、OPENAI_API_MODEL、OPENAI_API_TEMPERATURE、OPENAI_API_STREAM |
| `ai_set_credential` | `{key, value}` | 空串=清除；返回只有「配没配」 |
| `ai_test_connection` | `{provider, apiKey, apiUrl, model}` | `{ok, text, model, status, durationMs, emptyReason}`；失败是 `ok:false` 不抛 |
| `ai_get_lyric_lines` | `{musicId}` | `{lines:[{startTime,text}], source, hasWordByWord, maxLines}` |
| `ai_segment_lyric` | `{lines:[string]}` | `{boundaries, rejections, stats}`，进度走事件回传 |
| `ai_segment_progress` | — | 主进程→渲染层推送：`{phase, batch, batchCount, processed, total, provider}` |
| `ai_get_manual_prompt` | `{lines}` | 提示词全文（给没有 API Key 的用户复制到模型网页） |
| `ai_parse_manual_result` | `{lines, raw}` | `{boundaries, rejections}` |
| `ai_apply_lxlrc` | `{musicId, lines, boundaries, options?}` | `{ok, stats, usedFallback, message, lxlrc}` |

典型串法：

```
1. ai_get_lyric_lines {musicId}          → 拿到带时间的行
2. ai_segment_lyric   {lines: 行的 text}  → boundaries（同时订阅 ai_segment_progress）
3. ai_apply_lxlrc     {musicId, lines, boundaries}  → 写回 lxlyric
```

第 3 步只替换 `lxlyric`，原文 / 翻译 / 音译原样带回，不会覆盖用户已有的歌词。
返回值里额外带 `lxlrc`，是为了让渲染层直接 emit 给播放器即时刷新，不必等下次读库。

**新增依赖：零。** 全程用 `undici` 的 fetch（已有依赖）+ Electron 内置的 `safeStorage`，
没有模型文件、不要求 GPU。这也是当初选它当第一个功能的原因。

### 14.1 IPC 契约

| 事件 | 参数 | 返回 |
|---|---|---|
| `analysis_get_status` | — | `{platform, modelsDir, outputDir, manual, models, ready}` |
| `analysis_download_model` | `{name}` | `{ok, skipped?, path, freed?}` |
| `analysis_cancel_download` | `{name}` | `boolean` |
| `analysis_remove_models` | — | `{ok, removed, freed}` |
| `analysis_download_progress` | — | 主→渲染推送：`{name, status, received, total}` |
| `analysis_begin_job` | — | `{jobId, inputPath}` |
| `analysis_run_job` | `{jobId, total, name?}` | `{ok, vocals, accompaniment, stats, message, elapsed}` |
| `analysis_abort_job` | `{jobId}` | `boolean` |
| `analysis_job_progress` | — | 主→渲染推送：`{chunk, chunks, progress, ...}` |

三个字段要看清：

- **`ready` 是「能不能跑」不是「文件在不在」**。权重和解释器是两次独立下载，
  只有权重等于 109 MB 的摆设。`modelsPresent()` 就是为这个存在（`test-analysis.cjs` 第 3 组盯着它）。
- **`total` 是每声道的采样数**。主进程用它核对 `mix.in` 的长度（`total * 2 * 4` 字节），
  对不上就报「音频数据不完整」，而不是把半截数据喂给模型。
- **`progress` 是分块进度**，`chunk === 0` 表示模型还在加载（冷启动约十秒）。
  界面上这两句文案是分开的：「正在加载模型…」比一个停在 0% 的进度条诚实。

### 14.2 怎么复核产物（别只看「出了两个文件」）

```bash
python build-config/verify-stems-output.py                    # 默认读桌面上的「泛音分离」
python build-config/verify-stems-output.py <导出目录> <素材目录>
```

它拿产物与**已知源轨**做相关，并要求**真配对 ≫ 错配对**。2026-10-13 的实测结果：

```
人声 ↔ 源人声   0.9983        人声 ↔ 源伴奏   0.0334
伴奏 ↔ 源伴奏   0.9746        伴奏 ↔ 源人声   0.0254
```

只算一个方向会被「两轨都接近原混音」骗过去，所以两个方向都要比。脚本只用标准库
（`wave` + `array` + `math`）—— 这台机器上能跑 numpy 的是应用自带的那份运行时，
不该让一个校验脚本依赖它。

### 14.3 五个只有跑起来才知道的坑

1. **dev 模式的 userData 是 `%APPDATA%\Electron`，不是 `%APPDATA%\overtone`。**
   `npm run dev` 是 `runner-dev.js` 直接指定入口脚本启动 Electron 的，它不读 package.json 的
   `name`，于是 `app.getName()` 回落到默认的 `Electron`，`app.getPath('userData')` 跟着变。
   表现是「模型明明在盘上，对话框说没安装」。打包后才是 `%APPDATA%\overtone`。
   查模型时两个 profile 都要看（`probe-stems.py` 的 `runtime_python()` 就是这么做的）。

2. **模型目录必须一直显示在对话框里。** 镜像全挂时走网盘兜底，文案是「放到模型目录里」——
   不说清是哪个目录，用户只能猜。`get_status` 本来就返回 `modelsDir`，白加一行而已。

3. **对话框开着时切换歌曲，「当前歌曲」要跟着变。** 一开始写成打开时的快照，
   于是喂本地文件验收时显示的还是上一首。改成
   `const songTitle = computed(() => currentSongTitle())` —— `playMusicInfo` 是
   `shallowReactive`，赋 `.musicInfo` 会触发，computed 跟得上。

4. **这台机器没有音源，在线歌曲一律「换源失败」**（`user_api.json` 是空的 `{}`）。
   分离链路的真实验收只能用**本地文件**：本地音乐的 URL 走 `pathToFileURL`，不经过音源。
   而 `window.lxData.playMusicInfo`（`store/player/state.ts` 里挂上去的）可以在页面上下文里
   直接设当前歌曲 —— 分离读的就是它，**所以不必真的播放，不会有声音**。
   歌词区是唯一需要「已经渲染」的东西，因为入口挂在歌词的右键菜单里。
   详见 `build-config/drive-stems-local.js`。

5. **上一轮的对话框没关，会让下一次打开读到上一次的状态。** `modelValue` 一直是 `true` 时
   `watch` 不触发、`reset()` 不执行，读到的就是上一首的歌名和上一次的错误，
   看上去像「设置当前歌曲没生效」。驱动脚本里必须先点一次「关闭」再打开。

### 14.4 三个验收脚本的分工

| 脚本 | 验什么 | 要不要真跑 |
|---|---|---|
| `probe-stems.py` | 内核：混音素材 → runner → 相关系数 | 是（约 2 分钟） |

| `verify-stems-output.py` | 产物：两个 WAV 对不对 | 否 |

## 15. 入场动画：接线在哪、参数在哪、以及四个只有跑起来才知道的坑

### 15.1 它做了什么

启动链路上有一段真实的空窗（数据库初始化 → 主窗口创建 → 渲染进程加载），入场动画用一个
无边框透明小窗把它填上，主窗口就绪后淡出。

代码在 `src/main/modules/winSplash/`：`main.ts` 管窗口，`splash.html` 是页面。
页面是**纯静态 HTML + 内联 CSS/JS**，不需要 preload、不走 IPC，外观用 URL query 传入 ——
它必须在设置可读之前就能显示，所以不能依赖任何需要初始化的东西。

接线只有两处：

- `src/main/index.ts`：`init()` 里 `createSplashWindow()`（**抢在 `initAppSetting()` 之前**）
  与 `applySplashSetting()`（设置读完后刷真实外观）
- `src/main/modules/winMain/main.ts`：`ready-to-show` 里 `requestSplashClose()`

### 15.2 可定制项（都在设置 → 外观与个性化）

| 配置键 | 默认 | 说明 |
|---|---|---|
| `common.splashEnable` | `true` | 开关 |
| `common.splashMinMs` | `1400` | 最短显示时长（0.8 / 1.4 / 2 / 3 秒四档） |
| `common.splashImage` | `''` | 自定义启动图，建议透明 PNG、高约 88px |
| `common.splashTitle` | `''` | 标题文字，留空显示「泛音」 |

两个非常规设置项的实现参考：图片走 `showSelectDialog`（`src/renderer/utils/ipc.ts`）拿本地路径，
标题是输入框所以走本地副本 + `debounce` 落盘，不能每敲一个字写一次配置。

### 15.3 四个只有跑起来才知道的坑

1. **CSS 动画不能反向写。** `opacity: 0` + `animation: ... forwards` 意味着「内容全靠动画显示出来」——
   动画一旦不推进（窗口隐藏不参与合成、系统禁用动画），入场动画就退化成一个**纯黑方块**，
   比没有更难看。正确写法是基础状态可见、动画只负责从 `from` 淡入
   （`animation: rise 520ms 160ms backwards`）。详见 `06-个性化外壳.md` 第 6.1 节。

2. **隐藏窗口的动画不推进，截图拿不到画面。** `win.capturePage()` 之前必须 `showInactive()`，
   否则截到的是初始态（这正是发现坑 1 的过程）。

3. **`win.destroy()` 掉唯一窗口会触发应用退出。** `window-all-closed` 的默认行为是 `app.quit()`，
   之后任何 `loadFile` 都报 `ERR_FAILED (-2)`。要么复用一个窗口来回换参数，
   要么显式接管 `window-all-closed`。

4. **dev 的兜底上限要放宽。** 主窗口要等 webpack dev server 编译（本项目 40~60 秒），
   沿用生产环境的 15 秒会让入场动画提前收掉，看到的是「闪一下然后一片空白」。
   代码里按 `process.env.NODE_ENV` 分成 60s / 15s。

另外有一个**确认项**（不是坑，但值得记）：`splash.html` 是按 `path.join(__dirname, 'splash.html')`
找的，而这是本项目第一个在 dev 下依赖 `__dirname` 的功能（`winMain` 的 dev 分支走 http，从没用过它）。
`target: 'electron-main'` 下 webpack 默认保留真实值，prod 配置里那两行
`node: { __dirname: false }` 是同一件事的冗余声明。
**前提**是两个 webpack 配置的 `CopyWebpackPlugin` 都要加拷贝 —— 只加 prod 的话，
dev 里会永远报找不到 splash.html，和当初 `stems_runner.py` 是同一个坑。

### 15.4 三个验证脚本

| 脚本 | 验什么 | 怎么跑 |
|---|---|---|
| `probe-splash.py` | **时机**：splash 先出现、主窗口就绪后消失 | 先起它，再起 dev（带调试端口） |

### 17.2 改的时候容易踩的五个点

1. **`#left` 必须 `position: absolute`。** 少了这句，「收起」会变成「内容区被挤走一半」——
   `#container` 是 flex 容器、`#left` 是 flex item，宽度归零会让 `#right` 跟着重排。

2. **唤出热区的 `z-index` 要低于侧栏**（hotzone 19 / `#left` 20）。反过来的话，侧栏展开时
   最左边 8px 会被热区吃掉点击。
3. **`:has()` 在这里是必需品，不是炫技。** hotzone 与 `#left` 是兄弟节点，纯 CSS 只有
   `:has(#aside-hotzone:hover)` 能表达「hover A 影响 B」；鼠标从热区移到侧栏上之后由
   `#left:hover` 接管，否则会中途收回去。
4. **`View.vue` 的 `<transition>` 必须保留经典模式的分支。** 上游把这段过渡注释掉了，
   我们是「按模式打开」，不是「改成默认开」—— 经典模式要保持原样。
5. **`data-view="play-detail"` 锚点不要删。** PlayDetail 的容器类名是 CSS module 生成的，
   驱动脚本靠 `[data-view="play-detail"]` 判断播放页开没开。

## 18. 跟随封面取色：两个进程各干一半、以及一个必须知道的限制

### 18.1 数据键与接线

一个设置键 `common.coverColor`（boolean，默认 `false`），三处声明：类型 `app_setting.d.ts` /
默认值 `defaultSetting.ts` / 设置界面 `SettingAppearance.vue`（`base-checkbox`）。

一条链路四个落点：

| # | 落点 | 干什么 |
|---|---|---|
| 1 | `src/common/ipcNames.ts` | 新增 `coverColor.get_image` + 导出 `COVER_COLOR_EVENT_NAME` |
| 2 | `src/main/modules/coverColor/index.ts` | 读图 → 缩到 36×36 → 编码 PNG data URL（带 sha1 缓存，FIFO 24 条） |
| 3 | `src/renderer/utils/ipc.ts` | `getCoverImage(pic)` |
| 4 | `src/renderer/core/useApp/useCoverColor.ts` | watch 开关 + `musicInfo.pic` → 量化 → 写 `--cover-color` |

消费端两处：`AppBackground` 的 `.tint`（染色层）与 `.mask`（遮罩色）。

### 18.2 为什么活要劈成两半

- **读图必须在主进程**：渲染层要算颜色只能靠 `<canvas>` + `getImageData`，而被污染的 canvas
  会抛 `SecurityError`。封面的两种来源必然踩雷 —— 本地文件路径（`getMusicFilePic` 对大图会落到
  临时文件上，`file://` 是不透明源）、在线歌曲的 http 地址（没有 CORS 头）。
- **量化必须在渲染层**：`nativeImage.toBitmap()` 的通道顺序（BGRA / RGBA）在不同平台与版本上
  有歧义；`<canvas>` 的 `getImageData` 保证是 RGBA。

data URL 那条路不绕 IPC —— 它本身就是解码结果，几百 KB 的字符串复制一遍不值得。

### 18.3 变量为什么写在 `documentElement` 的内联样式上

**不能**写进 `setTheme` 用的那个 `<style>`：那个元素每次切主题都被整段重写，变量会被冲掉。
内联样式优先级天然最高，主题怎么切都盖不掉。

关闭开关时用 `removeProperty`，**不是**写兜底色 —— 消费端全写成 `var(--cover-color, 原有值)`，
「变量在不在」本身就是开关。`AppBackground` 的 `state.tint` 也是这么判断的。

代价：`AppBackground` 的 MutationObserver 要多盯一眼 `<html>` 的 style 属性，
否则切歌时那层不会重读（原本只盯主题的 `<style>` 元素）。

### 18.4 取色算法的三条硬规则

1. **不做平均色**：背景、留白、文字会把平均色糊成灰 —— 那正是封面最没信息量的颜色。
   实际是按色相分 12 桶、用 `s²·v` 加权，取最重的那个桶的加权平均。
2. **灰度封面不染色**：一个像素都没进桶就是黑白封面，灰度图没有色相，硬提饱和度等于凭空造色 →
   返回 `null`。
3. **只改饱和度与明度，色相不动**：饱和度托底 ≥0.35、明度夹在 0.32 ~ 0.8。
   色相才是「这首歌的味道」。

### 18.5 ⚠️ 限制：看得见看不看得起，取决于主题

染色层和遮罩都在**背景层**，透不透得出来取决于上层内容有多不透明。实测（默认主题）：

| 位置 | 挡在中间的东西 | 实测 |
|---|---|---|
| 主界面 | `#container` 的 `--color-main-background` | `rgba(255,255,255,1)`，只有标题栏那条带 alpha 的 `--color-app-background` 透得出来 |
| 播放详情页 | `.bg::after` 的 `--color-main-background` | `rgb(255,255,255)` → 截图中部像素 `(254,254,254)` |

**这不是 bug**：内容不透明时背景就不该透出来（壁纸功能同理）。
所以这个开关的实际强度 = **主题背景透明度 × 染色强度**。


七步：开关关着不染色 → 已知主色的封面取到同色相 → 换封面颜色跟着变 → 灰度封面不染色 →

## 20. 通透主题：两个背景色别再混、一个按钮、以及 dev overlay 这个坑

要解决的是「7.2 的壁纸和 7.4 的取色在默认主题下看不见」。改动很小，
但**前提是先把两个背景色分清** —— 混了就会改错地方。

### 20.1 两个背景色，各管一段

| 变量 | 是什么 | 默认主题的取值 | 谁在用 |
|---|---|---|---|
| `--color-app-background` | 容器底色（内容层**之下**） | `var(--color-primary-light-600-alpha-700)` → **alpha 0.3**，能透 | `App.vue` 的 `#container` |
| `--color-main-background` | 内容面板 / 播放详情页那层蒙版 | `rgba(255, 255, 255, 1)`，**全挡** | `PlayDetail/index.vue` 的 `.bg::after`，以及各类卡片 |

壁纸与取色的图层都在**背景层**，所以「看得见 / 看不见」完全由上面这两层决定。
默认主题下：主界面能透一点（容器底 0.3），**播放详情页被 100% 挡住**（蒙版不透明）。

⚠️ **`alpha-700` 不是 alpha 0.7。** `RGB_Alpha_Shade(p, c)` 在 `p > 0` 时取的是 `1 - p`：

```js
// src/common/theme/colorUtils.js
exports.RGB_Alpha_Shade = (p, color) => {
  ...
  a = 1 - p        // ← alpha-700 的实际值是 0.3，alpha-300 才是 0.7
  return `rgba(${r}, ${g}, ${b}, ${a.toFixed(2)})`
}
```

按字面读那个数字会正好读反，调透明度时容易改出完全相反的效果。

### 20.2 新增了什么

1. **两套内置主题**（`src/common/theme/createThemes.js`，跑 `npm run build:theme` 重建 `index.json`）：

```js
{
  id: 'overtone_glass',
  name: '澄澈泛音',
  isDark: false,
  config: {
    primary: 'rgb(79, 70, 229)',
    '--color-app-background': 'rgba(255, 255, 255, 0.35)',   // 容器更透
    '--color-main-background': 'rgba(255, 255, 255, 0.62)',  // 内容层半透明，壁纸才透得出来
    '--background-blur': '14',    // 半透明之上要有点模糊，文字才不跟壁纸细节打架
    '--background-mask': '16',
    ...
  },
}
```

两个背景刻意用**中性黑白**，不像默认主题那样从主色派生（`var(--color-primary-light-600-alpha-*)`）：
主色会稀释封面取色的色相，而通透主题的意义正是让歌的颜色当主角。

2. **主题编辑器壁纸分组里的「一键通透」按钮**（`ThemeEditModal/index.vue`）：
   只改 alpha、保留 RGB；点完顺手 `setMainBgColor()` 把基本组那个取色器同步过去，
   否则两个控件各说各话。深色档取 0.72 而不是 0.62（深色下内容层本来就更沉）。

3. **i18n 5 个新键 + 2 处改写**：脚本 `build-config/add-glass-i18n.py`。

⚠️ 语言包是 **CRLF**。整份重写时必须显式指定：

```python
io.open(path, 'w', encoding='utf-8', newline='\r\n').write(json.dumps(data, indent=2, ensure_ascii=False) + '\n')
```

用默认的 `newline=''` + `\n` 会把 4 个语言包的行尾整体退化成 LF，diff 直接爆成全文改动。
另外它们**不是字母序**（上游按语义分组排），所以也不能排序回写。

### 20.3 怎么验证

`build-config/drive-glass.js`，六步。两个要点：

**一、判定用像素，不用「读一下 CSS 变量对不对」。**

> 变量对 ≠ 看得见。这个功能的坑恰恰是「变量全对，但被上层一块不透明的底盖住了」，
> 只读变量会得出「一切正常」的错误结论。

脚本自带一个最小 PNG 解码（Node 内置 `zlib` + 四种反滤波），把截图解成像素直接量红度 `r - g`。

**二、`(async () => {...})()` 前面必须有分号。**

```js
const readMainBg = cdp => cdp.eval(`...`)

;(async () => {          // ← 这个分号不能省
```

少了它，`(...)` 会被解析成对上一行返回值的**函数调用**，整个 IIFE 变成箭头函数体的一部分、
永远不执行 —— 而 node 事件循环随之空掉，**静默 exit 0、零输出**，
看起来像「脚本跑了但什么都没打印」，极难往 ASI 上想。`node --check` 是过的。

留档图 `notes/preview/splash/22`~`25`（阶段 6 已占用 14~18，所以从 22 起）。

### 20.4 ⚠️ dev 的编译错误 overlay 会把每一张截图都废掉

只要 eslint 或编译报错，webpack-dev-server 就弹一个全屏 overlay 盖住整个界面，
截图随之变成一片暗色（实测中部平均 `rgb(52, 32, 35)`）。

它特别能骗人：**暗色很像「深色主题 / 深色壁纸生效了」**，而且 dev 日志、`build:renderer`
都可能看不出异常（两套独立编译）。第一遍跑就是这样挂了 12 项、还差点读成「功能正常」。

现在 `drive-glass.js` 起点会显式检查：

```js
const overlay = await cdp.eval("!!document.querySelector('#webpack-dev-server-client-overlay')")
if (overlay) throw new Error('dev 弹了编译错误 overlay（界面被盖住，截图全废），先修掉编译错误再跑')
```

新写驱动脚本时建议都带上这一句 —— 把「截图全废」这个隐性问题变成显式失败。

## 21. 清理内置平台接口（红线，2026-10-14）

### 21.1 删了什么

`src/renderer/utils/musicSdk/` 下：

| 路径 | 内容 |
| --- | --- |
| `kw/ kg/ tx/ wy/ mg/ bd/` | 六平台接口实现，**81 文件 / 411 KB** |
| `xm.js` | 虾米接口 |
| `utils.js` | 平台专用工具集（`toMD5` / `dnsLookup` / `formatSingerName`） |

`kg/vendors/infSign.min.js` 是**酷狗的签名算法** —— 最该消失的一个。

留在原地的都是框架：`index.js`（清空源表 + 保留通用搜索/排序骨架）、`api-source.js`
（分发点）、`api-source-info.ts`（本来就是空注册表）、`options.js`（`bHh` 请求头，
仍被 `utils/request.js` 用）、`versionChars.ts`（版本字符词表，被 `index.js` 的匹配算法用）。

### 21.2 为什么能安全删

调用点看起来很多（50+ 处 `musicSdk[source].xxx`），但**每一条都有护栏**：

| 护栏 | 位置 | 效果 |
| --- | --- | --- |
| `if (!music[id]?.xxx) continue` | 5 处 store 循环（search / songList / leaderboard / hotSearch） | 那些平台的 tab 自动消失 |
| `try { musicSdk[source].xxx } catch` | `core/music/utils.ts` 六处（取 URL / 封面 / 歌词） | 降级走「换源失败」分支 |
| `?.` 可选链 | 其余 40 余处 | 静默跳过 |

**只有一处没有护栏**，已补：`views/List/MyList/index.vue` 里
`musicSdk[source].leaderboard.getDetailPageUrl(id)` → 改成 `musicSdk[source]?.leaderboard?.(...)`。
（`handleOpenSourceDetailPage` 是 async，抛出来没人接这个 rejection。）

### 21.3 ️一个必须纠正的判断：「死代码」只说对了一半

清理前文档里写的是「这 411 KB 是死代码，没有任何调用路径能走到」。复核后发现：

- 取音频那条链（`getMusicUrl` / `getLyric` / `getPic`）**确实是死的** ——
  平台 `index.js` 里这几个方法只是 `return apis('xx').getMusicUrl(...)`，
  而注册表为空 → `getAPI()` 恒 `undefined` → `apis()` 抛 `Api is not found`；
- 但**搜索 / 榜单 / 歌单 / 热词是活的** —— `musicSearch` / `leaderboard` / `songList` /
  `hotSearch` 是真实实现，会直接请求平台服务器（`kw/index.js` 里就有
  `httpFetch('http://www.kuwo.cn/api/www/music/musicInfo?mid=...')`）。

所以这次清理不是打扫死代码，而是**拆掉一个还在通电的开关**。

### 21.4 功能性代价（不是意外）

搜索、榜单、分类歌单、热词、评论、换源候选**全部失空**。原因：它们都靠那些平台实现，
而自定义源协议（`useInitUserApi.ts`）只注册 musicUrl / lyric / pic 三种 action。

在线能力只剩「用户自行导入的源」；**本地音乐不受影响**（走 `apis('local')` →
用户源的 `local` 能力，与这次删除零关联）。

这条代价必须写进 README —— 用户第一次打开会发现「搜索是空的」，得让他知道
这是设计而不是坏掉。

### 21.5 零源适配：四层兜底（第一遍没做完的部分）

「删掉实现」只是第一步。上游从没跑过「零源」，所以**从删除那一刻起
`musicSdk[source]` 的取值就不再保证是个对象**。兜底按「由近到远」分四层：

| 层 | 位置 | 做什么 |
| --- | --- | --- |
| **默认值层** | `common/constants.ts` → `DEFAULT_SETTING` | 4 处硬编码的 `'kw'` / `'kw__16'` / `'new'` → 空串。否则**全新用户第一次打开**就是脏的 |
| **数据层** | `utils/data.ts` → `clearInvalidSourceField` / `clearBoundIds` | 读持久化设置时把失效 source 归一化成 `''`，页面自然走「没有可用源」分支 |
| **分发层** | `musicSdk/index.js` → Proxy 空壳 | `musicSdk[取不到的源]` 返回形状对齐的空结果；取音频/歌词/封面返回必然 reject 的 promise |
| **路由层** | 各页 `beforeRouteEnter` 守卫 | 搜索页把失效 source 回落 `'all'`（`'all'` 是聚合视图，要进白名单） |

**为什么「数据层」不能省** —— 页面守卫只在 `source == null` 时才去读设置；而
`getViewPrevState`（恢复上次视图）与深链接会把 `?source=kw` **显式**写进 URL，
直接绕过守卫。归一化必须在**读取处**做，只在路由处做会漏。

#### ⚠️ 空壳的「形状」只能从消费点反推

本轮最花时间的一处：**平台旧实现已删，没有文档可依，只能看消费点实际读什么字段**。
第一版按语义猜的形状，四处不合：

| 方法 | 猜的形状 | 实际要的 | 消费点 |
| --- | --- | --- | --- |
| `tipSearch.search` | `{ list: [] }` | **裸数组** | `Toolbar/SearchInput.vue` |
| `comment.getComment` | `{ list }` | `{ total, maxPage, comments }` | `PlayDetail/…/MusicComment/index.vue` |
| `songList.getTags` | `[]` | `{ tags, hotTag }` | `songList/List/components/TagList.vue` |
| `songList.search` | （整个漏了） | `{ list, total, limit, allPage, source }` | `store/search/songlist/action.ts` |

每一处不合都会让 `v-for` 拿到 `undefined` 而抛未捕获异常。`musicSdk/index.js` 里现在
有一张**空壳契约表**，改之前照着右列去核对消费点。

（另一个小坑：注释里写 `**allPage**/source` 时，那个 `*/` 会**提前闭合块注释**，
eslint 直接报 `Parsing error: Unexpected token *`。）

#### ⚠️ 验证必须从网络层正面取证

「界面上没有平台入口」不等于「不发请求」。用 CDP 的 `Network.requestWillBeSent`
记录后抓到一个真实请求：

```
http://img1.kuwo.cn/star/albumcover/300/s4s11/89/774616642.jpg
```

来源是**本机用户数据**（`OvertoneData/overtone.data.db` 里那首歌记着的封面地址），
不是代码内置的接口 —— 全仓源码 grep 平台域名 **0 命中**（只有注释里的示例头像 URL）。

因此断言分两级：

- **硬断言：平台「接口」类请求必须为 0** —— 这才是红线；
- **软报告**：图片类请求逐条打印（host 以 `img`/`pic`/`star` 开头，或路径以图片扩展名
  结尾），来自用户自有数据，按需人工确认。

README 里原来的「本项目自身不访问任何音乐平台的服务器」据此改成精确表述。
