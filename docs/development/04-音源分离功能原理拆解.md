# 音源分离功能 —— 原理拆解

> 对象：Folia 的「音源分离（Stem Separation）」
> 源文件：`electron/analysis/modelPaths.cjs`、`modelStore.cjs`、`sidecar.cjs`、`stems_runner.py`、`shared/modelManifest.json`
> 这份文档解释「它怎么工作」和「为什么这么设计」。移植时照此实现即可。

---

## 1. 这个功能到底做什么

**一句话：把一首歌拆成人声和伴奏两条独立的音轨，全程在本机完成。**

```
输入：小半.mp3（4 分 12 秒，立体声）
输出：小半 - 人声.wav   ← 只剩唱歌的声音
      小半 - 伴奏.wav   ← 只剩乐器
```

**为什么值得做？** 因为它是**不可替代**的：市面上做人声分离的服务要么收费，要么要求你把
整首歌上传到别人的服务器。而这件事**完全可以在本机做** —— 模型只有 109 MB，一台普通
笔记本就能跑。这正是当初把它选为「缝合的第一个能力」的原因：技术门槛真实存在，
且没有任何版权风险（用户处理的是自己本地的音频）。

**它的代价也很实在**：要下 109 MB 模型 + 36 MB 运行时，推理要花「一首歌一半时长」的 CPU。
所以界面上第一句话就写了「整个过程都在本机完成，不会上传任何音频」，第二句写
「四分钟的歌曲大约需要两三分钟」—— 两件事都提前说清，用户才不会误以为卡住了。

## 2. 完整链路

整个功能是**四段**，分属三个进程/解释器。分工的每一条边界都是被事实逼出来的，不是设计偏好。

```
① 模型与运行时（主进程，首次使用才走）
   modelManifest.json          声明：名称 / 字节数 / sha256 / 镜像
        │
        ▼
   modelStore.download()       按镜像轮换 + 断点续传 + sha256 校验
        │
        ├─ htdemucs.onnx        108,644,650 B
        └─ runtime/             zip 解压出 1380 个文件（含 python.exe）
        │
        ▼
   落到 userData/stems/

② 解码（渲染进程）
   currentSong()                当前播放歌曲（playMusicInfo.musicInfo）
        │
        ▼
   getMusicUrl({musicInfo})     ├─ local：pathToFileURL → file:///…
        │                        ├─ download：本地已下载文件
        │                        └─ online：音源接口（本机为空，会「换源失败」）
        ▼
   fs.readFile / fetch          拿到音频字节
        │
        ▼
   OfflineAudioContext(1,1,44100).decodeAudioData(bytes)
        │                        ← Chromium 自带解码器，mp3/flac/m4a/wav 全吃
        ▼
   写 mix.in                    裸 float32，布局 [ 左声道全部, 右声道全部 ]
        │                        ← 不是交错！见第 5 节

③ 推理（Python sidecar）
   stems_runner.py
        │
        ▼
   onnxruntime CPUExecutionProvider
   ├─ enable_mem_reuse = False
   └─ enable_cpu_mem_arena = False     ← 这两个开关决定了峰值内存
        │
        ▼
   按 4/4 重叠分块跑整曲，双桶累加
   ├─ vocals 桶
   └─ accomp 桶 = drums + bass + other
        │
        ▼
   write_wav(vocals) / write_wav(accomp)   16bit / 44100 / 立体声
        │                                   （先写 .part 再 os.replace）
        ▼
   stdout：每块一行 JSON 进度，最后一行汇总

④ 落盘（主进程）
   runStems()                   按行解析 stdout、转发 stderr、支持 abort
        │
        ▼
   moveOut()                    rename（同盘零拷贝）→ 失败退回 copyFile
        │
        ▼
   导出目录/泛音分离/歌名 - 人声.wav
                   歌名 - 伴奏.wav
```

## 3. 四层资产与各自职责

| 资产 | 大小 | 职责 | 能不能省 |
|---|---|---|---|
| `htdemucs.onnx` | 108.6 MB | 权重，ONNX 计算图 | 不能 |
| `runtime/` | 106.9 MB（zip 35.6 MB） | Python 解释器 + numpy + onnxruntime | **不能**（理由见第 6 节） |
| `stems_runner.py` | 9 KB | 分块、累加、写 WAV | 不能 |
| `sidecar.cjs` | 6 KB | 起进程、解析进度、超时、abort | 不能 |

**只有权重没有解释器 = 109 MB 的摆设。** 它们是两次独立下载，所以「装了没」这个问题的
正确答案是**两个都在**，而不是「.onnx 文件在不在」。`modelsPresent()` 就是为它写的：

```js
const modelsPresent = (dirs) => Object.fromEntries(MODEL_NAMES.map(name => [
    name,
    resolveModelFile(dirs, name) !== null && (name !== 'htdemucs' || runtimePresent(dirs)),
]));
```

漏掉这一条的表现很隐蔽：对话框亮着「开始分离」，点下去每次都以「还没下载运行时」拒绝。

## 4. 工程决策清单（每条都有实测数据）

### 4.1 为什么整曲分离不需要改 DSP

htdemucs 的输入窗口是固定的（`segment`），但 runner **本来就把长音频切块处理**：

```python
stride = segment - segment // 4          # 4/4 重叠相加
```

分块 + 三角窗归一化（overlap-add）是上游为「任意长度」准备的。所以「整曲跑一遍」
不需要动任何信号处理代码 —— **这一点当初判断错了会白白多写一堆重采样逻辑**。

### 4.2 双桶累加：整曲缓冲减半，结果逐位不变

上游只回传 drums / bass / vocals 三条轨（把 `other` 丢了），因为它的用途是「实时播放」，
只要这三条。而「伴奏」= `drums + bass + other`，所以必须自己留下 `other`。

朴素做法是开四个整曲缓冲、逐块累加、最后相加。但：

```
sum(stems) / w  ==  sum(stems / w)        # w 是分块归一化权重，对每块相同
```

所以「人声」和「其余三源之和」两个桶就够了，与逐位相加**等价**：

```python
vocals[:, start:end] += chunk[index["vocals"]]
accomp[:, start:end] += (chunk[index["drums"]] + chunk[index["bass"]] + chunk[index["other"]])
```

代价对比（4 分钟的歌，44.1 kHz 立体声 float32）：四缓冲 ≈ 4 × 85 MB = 340 MB，
双桶 ≈ 170 MB。**省下的正是峰值内存里最贵的那一段。**

### 4.3 两条产物必须共用同一个增益

```python
peak = peak_of(vocals, accomp)
gain = 1.0 / peak if peak > 1.0 else 1.0      # 只衰减，两条共用
```

如果各自归一化，人声与伴奏的**相对音量**就被破坏了 —— 用户把两条轨导入 DAW 时会发现
人声比伴奏响得离谱，而这个错误在单独试听任一条时都听不出来。

### 4.4 回传方式：让 Python 直接写 WAV

上游走 IPC 把三条裸 float32 轨传回主进程，再由主进程编码。整曲就是
`3 × 85 MB = 254 MB` 白搬一趟。现在 Python 自己写盘，主进程只拿两条路径。

留一个 `.part` 再 `os.replace`：`os.replace` 在同盘上是原子的，所以不会出现
「导出目录里有个半截 WAV」这种情况。

### 4.5 解码放在渲染进程，PCM 不走 IPC

| 方案 | 代价 |
|---|---|
| 主进程解码 | 得给 Node 再养一个 WASM 解码器（mp3/AAC/FLAC 各一套逻辑） |
| **渲染进程解码** | **零新增依赖** —— Chromium 自带 mp3/AAC/Opus/FLAC |

渲染层能直接用 `fs` 是因为主窗口是 `nodeIntegration: true` + `webSecurity: false` +
`sandbox: false`，webpack `target: 'electron-renderer'`。解出的 PCM **直接写 `mix.in`**
（85 MB 不走 IPC），主进程只收「路径 + 采样数」。

### 4.6 输入格式：非交错，而不是交错

```
mix.in = [ left(0..N), right(0..N) ]          ← 这样
       ≠ [ l0, r0, l1, r1, ... ]              ← 不是这样
```

交错与分块会互相打架：分块按整段切，交错之后「每块的第 0 个 float 是哪个声道」
取决于块长的奇偶。非交错则每块的两半天然对齐。

**单声道源要复制而不是补零** —— 补零会变成「右声道静音」，模型会把整首歌判成
只在左边，分离出来的人声也是单边的。这种错误听起来「有点怪」但不会报错。

### 4.7 采样率写死 44100

不是偏好，是导出图的形状决定的：`OfflineAudioContext(1, 1, 44100)` 建好后
`decodeAudioData` 会把源音频重采样到这个值，于是后面**不需要再做任何重采样**。
用一个假长度（`1, 1`）是惯例，Chromium 只看 `sampleRate`。

## 5. 核心精解：内存开关为什么决定架构

**这是整个功能里唯一「没有替代方案」的约束。**

onnxruntime 的 CPU 后端默认会开两个内存池：

| 开关 | 默认 | 关掉之后 |
|---|---|---|
| `enable_cpu_mem_arena` | True | 不再预分配大块竞技场（**光它自己就有 ~5 GB 峰值**） |
| `enable_mem_reuse` | True | 不做中间张量复用（复用会长时间持有缓冲） |

把两个都关掉，峰值工作集从 ~2.5 GB 降到 **543.2 MB**（实测整曲 89.9 秒）。
**这两个开关只有 Python 绑定能设。** onnxruntime-node 的 `extra` 选项只对 WASM 后端生效，
C API 也没暴露它们。

于是结论很直接：

> 要么接受 2.5 GB 峰值（4 分钟的歌在一台 8 GB 的笔记本上会很难看），
> 要么带一个 36 MB 的 Python 运行时。

选后者。这也解释了为什么这个功能**必须**有 sidecar 这一层：
它不是「用 Python 方便」，而是「只有 Python 能设这两个开关」。

实测数据（都在 ONNX Runtime 1.29.0 / numpy 2.4.6 上）：

| 场景 | 峰值工作集 | 推理耗时 | 相对实时 |
|---|---|---|---|
| 40 秒噪声窗口（14 块） | 488.9 MB | 24.7 s | 0.62× |
| 140 秒真素材 | 601.3 MB | 88.23 s | 1.54× |
| 89.9 秒真素材（走界面） | 543.2 MB | 51.67 s | **1.74×** |

「相对实时」小于 1 表示比实时快 —— 只有 0.62× 是噪声窗口的短测（模型加载占比高），
正常长度的整曲稳定在 1.5～1.8×。

## 6. 断点续传为什么是必需的

`modelStore.cjs` 的 `downloadTo()` 是这一版**唯一在上游基础上新增的逻辑**。
不是「优化」，是**必需**：

```
本机实测：hf-mirror.com / huggingface.co / github.com
         三个镜像都会在约 10 MB 处切断连接。
```

单次流式下载永不收敛 —— 每次都从 0 开始，每次都停在 10 MB。首版脚本的做法是
「失败了换下一个镜像」，结果是三个镜像轮完之后 `[FAIL]`，而**盘上其实已经有 45 MB 好数据**。

现在的做法是**原地重试 + 续传**：

```js
const resuming = response.status === 206 && offset > 0;
const base = resuming ? offset : 0;
if (!resuming && offset) await fsp.rm(part, { force: true }).catch(() => { });
const hash = await hashOfPrefix(resuming ? part : null);   // 只重算已落盘部分的哈希
const handle = await fsp.open(part, resuming ? 'a' : 'w');
```

三个细节：

1. **续传要接着算哈希。** `sha256` 是下载**唯一**的正确性依据 —— 截断或替换的 ONNX
   不会大声失败，它会正常加载然后给出错误音频。分片续传之后必须把已落盘部分的
   摘要接着喂给同一个 hash 对象，否则校验永远不过。
2. **服务端不认 `Range` 时要把半截文件删掉**（`!resuming && offset`），
   否则就是把两段不同的内容拼在一起，而且大小可能刚好对得上。
3. **只有 `received === model.bytes && digest === model.sha256` 才 rename 到最终名**。
   临时文件用 `.part` 后缀，成品名一旦出现就意味着「已经是校验过的完整文件」。

`.model-cache/fetch.py`（预下载工具）是同一套逻辑的另一份实现：
每次失败原地重试、镜像轮换、**无进展 31 次才放弃**。

## 7. 移植到 LX Music 的适配点

| 上游 | 这里 | 为什么 |
|---|---|---|
| 两个模型（beat_this + htdemucs） | **只有 htdemucs** | beat_this 服务的是 automix（节拍网格），我们没有这个功能 |
| 设置页里的模型管理 | 分离对话框内的两行 | LX 的设置页层级不同，放在功能入口处更直接 |
| `getDownloadDir()` | `app.getPath('userData')/stems` | 同一角色；**注意 dev 模式是 `%APPDATA%\Electron`** |
| 导出到固定目录 | `download.savePath` → `泛音分离/` | 用户已经告诉我们音乐放哪了 |
| 回传三条裸轨 | 直接写两个 WAV | 整曲 254 MB 不上 IPC |
| 逐源累加到四个缓冲 | 双桶累加 | 见 4.2 |
| 音源返回 URL 后交给播放器 | 渲染层解码成 PCM | 见 4.5 |

**文件名处理**是移植时新写的部分：歌名来自各个音源，什么都可能有。

```js
const ILLEGAL_FILENAME_CHARS = /[\\/:*?"<>|\u0000-\u001f]/g    // 控制字符是本意，不是手误
const sanitizeName = (raw) => {
  const text = String(raw ?? '').replace(ILLEGAL_FILENAME_CHARS, ' ').replace(/\s+/g, ' ').trim()
  return text.slice(0, 80).replace(/[. ]+$/, '')                // 资源管理器会吃掉结尾的点
}
```

斜杠会让 `path.join` **静默换目录**，所以这一层不能省。同名时 `uniquePath()` 让路
（` (2)`、` (3)`），而不是覆盖用户上一次的导出。

**`moveOut()` 先 rename 再退回 copyFile**：临时目录在系统盘、导出目录常在音乐盘，
跨盘 rename 会以 `EXDEV` 失败。不做「让 Python 直接写进导出目录」的省事方案 ——
那样用户会先看到一个中文名下的半截文件，而且 Python 侧还得处理非 ASCII 路径。

const decodeAudio = async(bytes: ArrayBuffer) => {
  const context = new OfflineAudioContext(1, 1, STEM_SAMPLE_RATE)

}

const writeMix = async(inputPath: string, audio: AudioBuffer) => {
  const total = audio.length
  const left = audio.getChannelData(0)
  const right = audio.numberOfChannels > 1 ? audio.getChannelData(1) : left

}

## 9. 移植时踩的坑

### 9.1 dev 模式的数据目录是 `%APPDATA%\Electron`，不是 `%APPDATA%\overtone`

最费时间的一个。`npm run dev` 走 `runner-dev.js` 直接指定入口脚本启动 Electron，
它不读 package.json 的 `name`，于是 `app.getName()` 回落到默认的 `Electron`，
`app.getPath('userData')` 跟着变成 `%APPDATA%\Electron`。打包后才是 `%APPDATA%\overtone`。

表现：模型下载、校验、落盘全都成功，**对话框还是说「未安装」**。

排查脚本因此要同时看两个 profile：

```python
for profile in ('Electron', 'overtone'):
    base = os.path.join(os.environ['APPDATA'], profile, 'stems')
    ...
```

### 9.2 对话框必须显示模型目录

网盘兜底文案说「放到模型目录里」，不说清是哪个目录，用户在三个镜像全挂的时候只能猜。
`get_status` 本来就返回 `modelsDir`，加一行而已。

### 9.3 「当前歌曲」要用 computed，不能用打开时的快照

```js
// 错的：打开对话框那一刻拍一张快照
const songTitle = ref(currentSongTitle())

// 对的：playMusicInfo 是 shallowReactive，赋 .musicInfo 会触发
const songTitle = computed(() => currentSongTitle())
```

喂本地文件做验收时，这个 bug 的表现是「明明设了 overtone-test，对话框显示上一首」。

### 9.4 驱动脚本要先关掉上一轮的对话框

`modelValue` 一直是 `true` 时，`watch` 不触发、`reset()` 不执行 —— 于是读到的
是上一首的歌名和上一次的错误信息，看上去像「设置当前歌曲没生效」。
脚本里先点一次「关闭」再打开，让这次是一次真正的 `false → true`。

### 9.5 Windows 上 `WinGet\Links\ffmpeg.exe` 是个 shim

Python 直接 `CreateProcess` 它会报 `WinError 193`（不是有效的 Win32 应用程序）。
要走到 `Packages\...\bin\ffmpeg.exe` 的真实路径。

## 10. 验证方式

### 10.1 三组验证，越靠后越接近真实

| 层次 | 工具 | 判据 |
|---|---|---|
| 状态判断 | `test-analysis.cjs`（20 项） | 只有权重不算能跑、平台变体折叠、超时策略、入参校验 |
| 内核 | `probe-stems.py` | 真素材按固定比例混音 → 跑 runner → **相关系数** |
| 界面 | `drive-stems-local.js --run` | 点击到出文件，全链路 |
| 产物 | `verify-stems-output.py` | 真配对 ≫ 错配对 |

### 10.2 为什么必须用相关系数

「听起来还行」不是判据。固定比例的混音素材给了我们**已知答案**：

```
人声 ↔ 源人声   0.9983        人声 ↔ 源伴奏   0.0334
伴奏 ↔ 源伴奏   0.9746        伴奏 ↔ 源人声   0.0254
```

**两个方向都要算。** 只算「人声 ↔ 源人声」，一个「两轨都接近原混音」的错误实现
（比如忘了减掉另一轨）也能拿到高分。要求真配对与错配**拉开 0.40 以上**，
这个错误就藏不住了。

`test-analysis.cjs` 里也有一组同理的断言：模型装没装、运行时装没装、
平台变体折进来没有 —— 这一类的失败**都是静默的**（对话框说能跑、跑起来才崩），
只能靠断言提前挡住。
