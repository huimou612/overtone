# AI 歌词功能 —— 原理拆解

> 对象：Folia 的「歌词分词（Lyric Word Segmentation）」功能
> 源文件：`shared/lyricSegmentationPrompt.cjs`（14.5 KB）、`shared/lyricSegmentationService.mjs`（12.8 KB）、`electron/aiTextClient.cjs`（33.7 KB）、`electron/aiCredentialStore.cjs`（7.4 KB）
> 这份文档解释「它怎么工作」和「为什么这么设计」。移植时照此实现即可。

---

## 1. 这个功能到底做什么

**一句话：把一行歌词切成「词」，并且保证切完拼起来和原文一字不差。**

```
输入：  把回忆拼好给你
输出：  ["把", "回忆", "拼好", "给", "你"]
```

**为什么要这么切？** 因为 Folia 的歌词动画是**逐词高亮**的——要做出「字一个一个跳出来」的效果，必须知道每个词的边界在哪。而中文没有空格，机器不知道「回忆」是一个词还是两个字。

**这就是整个功能的立身之本**：不是「翻译歌词」「润色歌词」，而是**分词**。选择这个任务很聪明——它：
- 是机械任务（不需要创造力）→ 可以用便宜、快速的模型
- 有客观正确性（能无损还原）→ 能自动校验
- 一次做完永久缓存 → 成本极低

## 4. 工程决策清单（每条都有实测数据）

这些注释是**这个项目最值钱的部分**——真金白银的实测经验：

| 决策 | 实测依据 |
|---|---|
| Gemini 关掉思考（`thinkingBudget: 0`） | 开思考 9.0s，关掉 1.6s，**输出字节完全相同**。分词是机械任务，没有可推理的东西 |
| `reasoning_effort: 'none'` | deepseek-v4-flash 不加这个：把整个 token 预算烧在推理上，52 秒后返回**空答案**；加上：约 1 秒出结果 |
| `'minimal'` 不管用 | 实测 `reasoning_effort: 'minimal'` 仍会烧完全部预算。必须是 `'none'` |
| 必须有 Gemini schema | 不约束输出形状时模型会自我重复：同一个 12 行请求三次测得 **7KB / 14KB / 37KB**，延迟 **8s / 16s / 42s**，长度和延迟同步增长 |
| 输出上限 8192 tokens | 实测约 18 tokens/行（150 行 → 2707 tokens），100 行一批远在预算内 |
| **日语规则 + 2 个日语示例是「承重」的** | 只有中英示例时，弱模型把英文行理解成「按空格切」然后套用到所有语言。deepseek-v4-flash 在 19 行日语上，5–10 行原样返回不切（1.6–2.4 段/行，而 `Intl.Segmenter` 给 7） |
| 抽象规则没用，示例才有用 | 光加一条「绝不返回整个从句」的抽象规则：**没有改善**（仍有 9 行未切）。加上日语规则 + 两个日语示例行：降到 1 行未切、3.8 段/行 |
| **这个改动不是日语专属** | 加上后中文**不再过度分割**（「摘不下」「盒子里」作为整体保留），英文输出**字节级相同**。Gemini 同样受益：2.8 → 3.4 段/行 |
| 规则 7 的括号条款 | 不加的话新增规则会把 `(拼图女孩)` 拆成三段 |
| 400 行上限 | 请求体守卫，在任何凭据或网络操作**之前**校验 |

**给移植的启示：** 提示词工程在这里不是「写一段话让模型干活」，而是**用实测数据驱动的迭代优化**。你要改规则时，也必须做同样的对照测量。

## 5. 核心精解：`realignSegmentsToText`

**这是整个功能最精彩的一处设计。**

### 问题

模型有个稳定行为：**分割点给得很准，但会顺手把空白字符规范化**——
- 丢掉行尾空格
- 把全角空格折成半角
- 把连续两个空格压成一个

如果直接拿「拼接结果 === 原文」做校验，那么**一个装饰性差异就会让整首歌被丢弃**。

### 解法

> **不信任模型返回的文本，只信任它的边界。**

做法：拿着**原文**走一遍，按模型给的分段去消费原文里的非空白字符，让原文自己的空白落回它实际所在的位置。

结果：每个分段都是原文的一个切片，**它们的拼接必然等于原文——由构造保证，而不是靠模型表现良好。**

只有在**非空白内容真的不一致**时才返回 `null`（模型改写、翻译、漏词），这才是真正该失败的场景。

### 为什么值得学

| 思路 | 说明 |
|---|---|
| 区分「实质」与「装饰」 | 分割点是实质，空白是装饰。只校验实质 |
| 把正确性变成构造性质 | 与其事后校验（可能误杀），不如构造时就保证 |
| 保留真正的失败检测 | 不因为容忍装饰就放过改写 |

这个思路可以直接搬到别的 LLM 结构化输出场景。

## 6. 凭据安全（`aiCredentialStore.cjs`）

**用户要填自己的 API Key，所以密钥管理是绕不开的。Folia 的做法值得照抄：**

| 措施 | 实现 |
|---|---|
| 落盘加密 | Electron `safeStorage`（Windows 走 **DPAPI**、macOS 走 Keychain、Linux 走 libsecret/kwallet），磁盘上只有密文，字段名加 `_SEALED` 后缀 |
| **渲染层永远拿不到明文** | 前端只知道「这个 key 存了没有」（`AI_API_KEYS_CONFIGURED`），表单提交新 key 时传明文，清空时传空串 |
| 防越权写入 | `isReservedAiCredentialKey` —— 密文和状态字段名不允许渲染层写入 |
| 惰性解密 | Linux 上 `safeStorage` 必须等 `app.whenReady()` 之后才可用 |
| 明文迁移 | `migrate()` —— 把旧版本留下的明文 key 重新加密 |
| 防密钥外泄 | `resolveTestApiKey` —— 只有在 URL 与已保存的一致时，才把保存的 key 用于「测试连接」。避免用户改了 URL 后，key 被发到从未授权的主机 |
| 解密失败降级 | 密文来自别的机器/用户，或钥匙串暂时锁着 → 不缓存、不删密文，等钥匙串解锁后自动恢复 |

**这套设计对缝合项目的价值：** 你要做 AI 功能就必须处理 API Key，直接照抄这一套，能省掉一整个安全评审。

## 7. 一个贴心的兜底：手动模式

`buildSegmentationManualPrompt(lines)` 生成的提示词**可以直接复制到任意模型网页**，让模型用 `/` 分隔符返回纯文本：

```
（8 条规则全文）
If you cannot produce JSON, answer with N plain lines instead,
separating words with "/" and nothing else.

Segment these N lyric lines.

1. 把回忆拼好给你
2. ...
```

**这意味着：用户没有 API Key 也能用这个功能。**

对缝合项目来说这是个很好的设计——降低了使用门槛，也让功能在「用户不想配 key」时仍然可用。移植时**务必保留这条路径**。

按第 9 章的骨架实现完了，但落地时有两处和原计划不同：

| 计划 | 实际做法 | 原因 |
|---|---|---|
| 手工搬文件 | `build-config/port-folia-src.py` 脚本化搬运 | 4 个文件 1600+ 行，手工搬必然引入无声差异。脚本只做三类改动（require 路径、`.mjs`→`.cjs`、加版权头），其余逐字保持，日后同步上游可以直接 diff |
| 用 `runAiJsonCompletion` 单次请求 | 外面套一层 `service.cjs` 分批（100 行/批） | 桌面端用户填的可能是任何模型，一次丢几百行的失败面太大；且没有进度可报，长歌界面会干等 |

落地文件（`src/main/modules/ai/`）：

```
segmentation.cjs            上游 shared/lyricSegmentationPrompt.cjs     逐字移植
textClient.cjs              上游 electron/aiTextClient.cjs              逐字移植
credentialStore.cjs         上游 electron/aiCredentialStore.cjs         逐字移植
openAICompatibleRequest.cjs 上游 shared/openAICompatibleRequest.mjs     逐字移植（转 CJS）
lxlrc.cjs                   新写  分词边界 → lxlrc 时间轴
service.cjs                 新写  分批、进度、失败隔离、凭据与设置
index.ts                    新写  LX 的 IPC 契约（10 个事件）
```

**为什么用 `.cjs` 而不是 `.ts`：** LX 主进程是 webpack 打包的，只有 `.ts/.tsx` 走
ts-loader，`.cjs` 由 webpack 原生按 CommonJS 解析——所以移植文件可以保持与上游同构。
反过来若重写成 `.ts`，就再也无法和上游对照了。

另外 `customFetch` 在上游是**必填**（Electron 主进程直接传全局 fetch）。本项目不能
这么假定：Win7 版本跑 Electron 22（Node 16，没有全局 fetch）。所以 `service.cjs` 里
做了 `resolveFetch()`，优先取 **undici 的 fetch** 而不是全局的 —— 这样能顺带拿到
LX 已配置的代理（LX 的 `common/utils/request` 在用户配代理时调 undici 的
`setGlobalDispatcher`，webpack 打的同一份 undici 实例，共享 dispatcher）。

## 11. ★ 移植时踩的坑：lxlrc 格式契约（全部实测得出）

这一节是这次移植最有价值的产出。**下面每一条结论都是跑代码验证出来的，不是读文档
推出来的**——因为搞错的失败模式是「不报错，但功能悄悄没了」。

探测脚本：`build-config/probe-lxlrc-format.cjs`
（复刻上游解析逻辑，直接打印各种输入字符串的解析结果）

### 11.1 时间基准是相对行首，不是绝对时间

格式：`[mm:ss.mmm]<起始毫秒,时长毫秒>词1<起始毫秒,时长毫秒>词2…`

依据有两处，互相印证：
- 生成侧：三个平台解析器（`musicSdk/{wy,tx,mg}/lyric.js`）都做了
  `parseInt(start) - startMsTime`，减掉行起始
- 消费侧：`lyric-font-player/index.js` 里 `font.play(curTime - this._lines[num].time)`
  —— 传给 FontPlayer 的时间基座已经减掉了行时间

### 11.2 每一行都必须以 `<数字,数字>` 开头（最容易踩的一条）

解析端是这么切分的：

```js
const fontSplitRxp = /(?=<\d+,\d+>).*?/g
fonts = lyric.split(fontSplitRxp)
for (const font of fonts) {
  if (!timeRxp.test(font)) return this._handleLineParse()   // ← 整行退化
  ...
}
```

关键在 `_handleLineParse()` 的实现：

```js
_handleLineParse() {
  this.isLineMode = true
  this.lrcContent.textContent = this.lyric    // ← 原始字符串，含尖括号标记
}
```

也就是说，**一行只要不是以 `<d,d>` 开头，整行会退化成普通模式，并且把
`<0,500>` 这样的时间标记原样当成歌词文字显示给用户**。不报错，只是画面很难看。

> 实测确认：`'把<0,500>回忆'` → 整个字符串被当正文；
> `'<0,500>把<500,300>回忆'` → 正确切成 2 段。

### 11.3 空行必须写成 `<0,0>`

`index.js:117` 用一句话决定整首歌是否逐字模式：

```js
this.isLineMode = lyricLines.length && !/^<\d+,\d+>/.test(lyricLines[0].text)
```

**只看第一行。** 所以如果第一行是空字符串，全曲会静默退回逐行高亮 —— 用户明明
生成成功了，效果却和没做一样。

写成 `<0,0>` 有两个好处：满足 11.2 的约束（该行本身不退化），以及让全曲闸门通过
（首行带标记）。而它的解析结果是「字体模式 + 空文本」，不会显示任何东西。

### 11.4 裸的 `<` 其实是安全的（这条是测试纠正的）

一开始我把校验写成「正文里不能有 `<`」，结果是过严的。解析端是**按
`(?=<\d+,\d+>)` 切分**的，正文里的 `<` 只要不构成 `<数字,数字>` 就不会被误切。
实测 `'1 < 2 > 0'` 可以逐字无损还原。

**真正的约束**只有一条：正文里不能出现形如 `<123,456>` 的子串。它会被解析端
当成段边界，导致段边界与构造时不一致、标记泄漏进正文。

这属于格式自身的歧义（原文真想包含这个子串就无从表达），所以 `lxlrc.cjs` 的处理是
**计数告警 + 跳过该行的自检，而不是抛错** —— 一行怪文本不该让整首歌失败。

### 11.5 时间怎么分配（AI 只给分词，不给时间）

- 行可用时长 `span` = 下一行起始 − 本行起始（末行用 `fallbackSpanMs` 兜底）
- `span` 先被 `maxLineSpanMs`（默认 6 秒）截断。不截断的话，行与行之间的间奏会
  把最后一个词拉成十几秒的慢动作高亮
- 每个词的权重 = 词内**实义字符数**（字母/数字/汉字算 1，空白标点算 0，下限 1）。
  按权重比例分配，最后一个词吃掉余数，避免行尾死等

### 11.6 测试怎么写才有意义

只断言「输出结构合法」是**不够的**：非法标记导致的失败模式恰恰是「静默退化成整行」。

所以 `build-config/test-lxlrc.cjs` 把生成的 lxlrc **喂回一个忠实复刻的上游解析器**
（从 `font-player.js` 的 `_parseLyric` 和 `index.js:~117` 抄出判定逻辑），同时断言三件事：

1. 全曲逐字模式闸门通过
2. 每一行都解析成字体模式（而不是退化成整行）
3. 解析出来的文字拼回去，与原始歌词**逐字一致**

第 3 条是关键：它是唯一能区分「真的逐字渲染」和「悄悄退化成整行」的断言。

### 11.7 还没有做的事

现在的时间轴是**按字重推算的近似值**。如果音源本来就带逐字歌词
（`source === 'lxlrc'`），可以拿**真实的词级时间**去和 AI 的分词边界做重组：
把 AI 的每段当作「一段要消费的连续词序列」，在真实词时间轴上找对应区间。
这样得到的就是精确时间轴。

`ai_get_lyric_lines` 已经把 `hasWordByWord` 报出来了，接口是留好的，只是还没接。

## 13. 渲染层：界面怎么接进来

主进程侧的能力（第 10~12 章）已经能用，但用户看不见。第 13 章把三个入口接上。

### 13.1 三个入口，各管一段

```
设置 → AI 歌词分词          配置提供方 / 密钥 / 接口地址 / 模型 / 温度 / 流式，并测试连接
播放详情 → 右键歌词 → 菜单   入口按钮，打开分词对话框
分词对话框（Modal）           读歌词 → 分词（自动 / 手动）→ 预览 → 写回
```

对应文件：

| 层 | 文件 |
|---|---|
| 设置面板 | `src/renderer/views/Setting/components/SettingAi.vue` |
| 设置页挂载 | `src/renderer/views/Setting/index.vue`（加一个导航项，`<component :is>` 自动解析） |
| 菜单入口 | `src/renderer/components/layout/PlayDetail/components/LyricMenu.vue` |
| 分词对话框 | `src/renderer/components/layout/PlayDetail/components/AiLyricModal.vue` |
| 类型声明 | `src/common/types/ai.d.ts` |
| IPC 封装 | `src/renderer/utils/ipc.ts` 末尾「AI 歌词分词」段 |

### 13.2 十个 IPC 事件（界面 ↔ 主进程的全部接触面）

| 事件 | 入参 | 返回 |
|---|---|---|
| `ai_get_status` | — | `{provider, encrypted, credentials, settings, limits}` |
| `ai_set_setting` | `{key, value}` | `settings` |
| `ai_set_credential` | `{key, value}` | `{OPENAI_API_KEY: bool, GEMINI_API_KEY: bool}` |
| `ai_test_connection` | `{provider, apiKey?, apiUrl?, model?}` | `{ok, text?, model?, status?, durationMs?, emptyReason?, error?}` |
| `ai_get_lyric_lines` | `{musicId}` | `{lines: [{startTime, text}], source, hasWordByWord, maxLines}` |
| `ai_segment_lyric` | `{lines: string[]}` | `{boundaries, rejections, stats}` |
| `ai_segment_progress` | 主进程 → 渲染层推送 | `{phase, batch, batchCount, processed, total}` |
| `ai_get_manual_prompt` | `{lines}` | `string` |
| `ai_parse_manual_result` | `{lines, raw}` | `{boundaries, rejections}` |
| `ai_apply_lxlrc` | `{musicId, lines, boundaries?, options?}` | `{ok, stats, usedFallback, message, lxlrc}` |

三处容易写错、已实测确认的地方：

1. **`mainHandle` 第二个参数拿到的是 `{ event, params }`**，所以主进程侧一律
   `async({ params }) => ...`，业务字段在 `params` 里面。
2. **`rendererOn` 把回调包成 `{ event, params }`**，所以渲染层订阅要写
   `onAiSegmentProgress(({ params }) => ...)`。
3. **`boundaries` 是「每行的词数组」`Array<string[] | null>`，不是下标数组。**
   单词数组里的每一项就是该段的文字，拼起来必须等于该行原文
   （主进程的 `realignSegmentsToText` 负责保证这一点）。

### 13.3 「密钥只进不出」在界面上怎么落地

这不是口号，是三处具体约束：

- `ai_set_credential` 的返回只有布尔量。界面拿到「配没配」，永远拿不到明文。
- 输入框是单向的：`credentialInput` 只出不进 —— 保存成功后立刻清空，不清空就等于
  把密钥留在 DOM 里；`getAiStatus()` 回填时也**不**往里写任何值。
- 「测试连接」用的是**表单里当前这个值**（`credentialInput`），不是已保存的那个。
  这样「测试通过」才真的意味着「接下来能跑通」。表单没填 key 时才回退用已保存的，
  而且只在 URL 未变的前提下回退（避免密钥被发到没授权过的主机，判断在
  `credentialStore.cjs` 的 `resolveTestApiKey`）。

界面上给的两个提示也如实反映后端能力：`encrypted` 为假时明确写「密钥将以明文写入
本机配置文件」，不假装安全。

### 13.4 写回之后，播放器怎么立刻变

只写数据库是不够的 —— 播放器不会自己重读。链路是：

```
AiLyricModal.apply()
  → ai_apply_lxlrc（主进程写库 + 把 lxlrc 一起返回）
  → emit('updateLyric', { lxlrc, message })
  → LyricMenu.handleAiLyricSaved()  ← 补齐 lyric/tlyric/rlyric/offset 后转发
  → LyricPlayer.handleUpdateLyric()  ← 上游既有实现
  → setMusicInfo({ lrc, tlrc, rlrc, lxlrc })  ← 播放器立刻出逐字效果
```

`ai_apply_lxlrc` **只替换 `lxlyric`**：写库时把读出来的 `lyricInfo` 整体展开再覆盖
`lxlyric`，原文、翻译、音译都原样保留。用户之前手工调过的行不会被抹掉。

注意 Vue 事件名：`emit('updateLyric')` 在模板里写成 `@update-lyric`。
上游同一对文件（`LyricMenu.vue` → `LyricPlayer.vue`）就是这么写的，所以这是本项目
既有约定，不是笔误。

### 13.5 组件与工具的既有约定（别再自己找一遍）

- 基础组件**全局自动注册**：`src/renderer/components/index.js` 用
  `require.context` 扫全部 `.vue`，组件名 = `upperFirst(camelCase(路径))`。
  所以 `<base-btn>` → `base/Btn.vue` → `BaseBtn`，`<material-modal>` → `material/MaterialModal`。
  写 `.vue` 时**不需要 import** 基础组件，但**自己新建的组件要显式 import**。
- 弹窗用 `material-modal`，props：`show / teleport / width / height / maxWidth / maxHeight /
  bgClose / closeBtn`，事件 `@close`。歌词里其他弹窗用 `teleport="#view"`。
- 剪贴板：`clipboardWriteText` 来自 `@common/utils/electron`。
- 确认框：`dialog.confirm(message)` 来自 `@renderer/plugins/Dialog`，返回 `Promise<boolean>`。
- 防抖：`debounce` 在 `@common/utils/common`，但 `@common/utils` 有
  `export * from './common'`，两种导入都行。
- Vue API 从 `@common/utils/vueTools` 导入，不是直接从 `vue`。

### 13.6 类型声明为什么要动两处

`tsconfig` 的 `typeRoots` 是**按模块隔离**的（`src/<模块>/types`），且每个模块的
`common.d.ts` 里要**逐行显式 import** 才生效。新增 `src/common/types/ai.d.ts` 后必须补：

```ts
// src/renderer/types/common.d.ts
import '@common/types/ai'
// src/main/types/common.d.ts
import '@common/types/ai'
```

漏了这一步的报错长这样：`Property 'Ai' does not exist on type 'typeof LX'`。
这是本轮踩过的坑之一。

### 13.7 验证方式（没有真机跑通前，至少要过这些）

```bash
npm run lint          # 全量 eslint，包含 webpack 自带的那份
npm test              # 54 项：lxlrc 构造/解析 + 编排层（假 fetch 离线跑）
npm run build:main    # 主进程
npm run build:renderer # 渲染层：webpack 会真的编译模板 + 跑 ESLint 插件
```

`build:renderer` 是本轮最有效的门禁 —— 模板里的组件解析、`<script>` 里的导入、
类型检查都会在这里暴露。集成测试里查不出来的接线错误基本在这一步被抓到。

### 13.8 已知限制

`rendererOff(name, listener)` **实际不生效**：`rendererOn` 传给 `ipcRenderer.on` 的是一个
新的箭头函数，不是 `listener` 本身，所以 `removeListener` 匹配不上。这是上游既有问题，
全项目都在用同一套封装。

对本功能的影响：对话框关闭后进度监听仍挂在 IPC 上。处理方式是回调里加一道守卫
（`if (!props.modelValue) return`），界面行为不受影响。要根治就得改
`src/common/rendererIpc.ts` —— 那会波及全项目，不做。
