# 06 · 个性化外壳

这份文档回答两件事：

1. 用户提的「双模式（经典洛雪界面 / 个性 Folia 界面）+ 可定制入场动画 + 壁纸」这个方案
   **到底贵在哪**，以及为什么它不是一件事而是三件。
2. 阶段 7.1「入场动画」是怎么实现的，以及过程中踩到的坑。

所有数字都来自实际清点（`git diff`、源码统计、真机实测），没有估算值。

---

## 1. 用户提案的拆解

原话要点：

> 「点开有我们泛音的入场动画，这个动画可以定制；可以弄一个入口，里面可以放壁纸。
> 既然是洛雪和 Folia 缝出来的，就做一个模式选择 —— 经典模式套洛雪界面，个性模式用 Folia 的界面。
> 音频功能（音源分离）也可以加上去。」

拆开后是三件独立的事，成本差一个数量级：

| 块 | 现状（已核查） | 成本 |
|---|---|---|
| 入场动画 | LX **完全没有**。`src/main/modules/winMain/main.ts` 只创建主窗口（`show: false` 等 `ready-to-show`），无 splash 窗口、无首屏遮罩 | 低，纯新增 |
| 动态壁纸 | LX **已有静态版**：主题编辑器的「背景图片」(`theme_edit_modal__bg_image`)，18 个内置主题 + 10 个自定义主题槽 + 23 个可调项 | 低，是升级不是重造 |
| 双模式界面 | 无。且外壳是 Vue、Folia 界面是 React | 取决于做法，最高到「极高」 |

两处容易误判的细节：

- **Folia 的 `AppSplashGate.tsx` 不是入场动画**。它只有 408 字节，作用是「首帧渲染完成后把
  `index.html` 里内联的遮罩淡出 320ms」（`utils/appSplash.ts`）。这是**遮白**，不是动画。
  真正管启动流程的 `hooks/useStartupExperienceGate` 管的是发布说明/引导，也与动画无关。
  所以「入场动画」在两边都没有现成可抄的。
- **Folia 的 `components/wall/` 不是壁纸**。从文件名看（`WallToolsQueueIsland`、`useWallPointerPan`、
  `flipPlan`、`seamPlan`、`blockReflows`、`rankSlots`）它是一套**无限画布式的内容墙**
  （拖拽 / 平移 / 翻牌），是 Folia 的主界面，跟桌面壁纸无关。

## 2. 「用 Folia 的界面」到底有多重

Folia 源码在 `fusion-music/reference/folia-major`（不在本仓库内），以下是清点结果：

| 项 | 数量 |
|---|---|
| React 组件 | **457 个 tsx**（`components/` 354、`library/` 80、`mods/` 19） |
| 状态层 | **40 个 zustand store** |
| 可视化器 `components/visualizer/` | **407 文件 / 6.97 MB**（@react-three/fiber + drei + postprocessing + @paper-design/shaders） |
| 招牌格子歌词 `components/app/lattice/` | 32 文件 / 148 KB（canvas 渲染） |
| 主界面 `components/wall/` | 35 文件 |
| 动画 / 样式 | framer-motion + animejs；Tailwind v4 |

而泛音的外壳是 **Vue 3**。「组件不能互搬」这条在阶段 0 就写进方案了，但当时没料到会想直接换壳。

### 真正的成本不在画界面，在状态

播放状态活在 Vue 的模块级响应式里（`window.lxData.playMusicInfo` 那一套），React 侧完全看不见。
要让两个壳共享「同一首正在播的歌」，只有两条路：把播放 / 队列 / 歌单**下沉到主进程**（等于重写
LX 的数据层），或者做一层**数据中继**（两个渲染进程都跟主进程要数据，但要自己处理一致性与真相源）。
两条都不便宜。

### 我去数了 lattice 的依赖，结论和预期相反

原本以为 Folia 的招牌视觉（动态歌词）是自包含的 —— 输入音频+时间轴+歌词、输出 canvas，边界很干净。
实际把 `components/app/lattice/` 的外部 import 全数出来之后：

| 类别 | 实际情况 |
|---|---|
| 必带的核心 | `visualizer/monet/monetLyricsModel`、`monetLyricMotion`（8 处引用） |
| 必须带的状态 | `useLatticeSettingsStore`、`useLatticeControlsStore`、`useWallHandoffStore` |
| 宿主耦合（可裁） | `components/wall/layout`（7 处）、`WallBackButton`、`WallToolsButton`、`WallToolsRows`、`ProgressBar`、`floating-player/playerControlSlotActions` |
| 意外触点 | `services/onlineMusic/songMetadata` |
| 包依赖 | react、framer-motion、**pixi.js**、react-i18next、lucide-react |

而且 `LatticeLyrics.tsx` 只有 1826 字节 —— 它的数据**不从 props 来**，是从 `useLatticeLyrics()`
这个 Provider context 拿的。所以切片不是「搬过来就能用」，而是「搬过来 + 裁掉宿主耦合 + 改成 props 驱动」。

## 3. 四种做法与推荐

| 做法 | 实质 | 成本 | 拿到什么 |
|---|---|---|---|
| 真双壳 | 两个渲染入口，Vue 一套 React 一套 | **极高**：播放状态层要重写到主进程 | Folia 的完整界面（含无限画布内容墙） |
| **切片复用**（推荐） | React 只装一个视觉模块，用 webview 嵌进 Vue | 中高：要做依赖闭包提取与裁剪 | Folia 最值钱的歌词视觉 |
| Vue 重写 | 只借设计语言，界面全部自己写 | 中 | 神似，但拿不到 Three.js/着色器那套 |
| 单壳双皮肤 | 外壳不变，做两档皮肤与动效强度 | 低 | 观感上的「个性」 |

### 为什么推荐「切片复用」

**做法 1 用大约 20% 的成本拿到 80% 的「这就是 Folia」观感** —— 人对「这是哪个软件」的判断，
八成来自播放页那一眼（动态歌词 + 3D 背景），不来自侧栏有几个菜单。

但要说清两点：

1. **做法 1 是做法 3 的第一段，却不会自动通向做法 3**。做法 3 的成本大头是状态中继，
   它不会因为先做了做法 1 而减少一分。所以别把它当「分两步就能到达」，那是虚假的乐观。
2. **做法 3 真正的风险不是技术，是功能不对称**。Folia 的定位是「一个动态歌词播放器」，
   它的信息架构里没有歌单管理 / 本地音乐 / 下载 / 批量编辑 / 设置体系这一整套。
   真双壳最后会撞上：个性模式里放不放这些？放进等于重写一遍功能 UI；不放进，
   用户切过去发现少一半功能，**反而比只有一套界面更差**。

### 所以个性模式做「沉浸形态」，不做「第二套界面」

> **经典模式** = LX 原样（管理为主，信息密度高）
> **个性模式** = 同一套界面的**沉浸形态**：侧栏收起、播放页全屏、歌词换成 Folia 的 lattice 视觉、
> 入场动画与动态壁纸生效

功能一个不少，只是「管理态」和「沉浸态」的差别 —— 这才是真实用户会来回切的两种状态。
技术上它正好是**阶段 7（Vue 侧）+ 阶段 8（切片）**的组合，且不需要状态中继。

## 4. ⚠️ 红线被加重了（这一节比成本问题重要）

清点依赖时发现：**Folia 自己内置了四家平台的音源实现**。

- `electron/neteaseBackend.cjs`、`neteaseApiStartup.cjs`
- `electron/qqBackend.cjs`、`qqApiStartup.cjs`
- `electron/bodianApiBridge.cjs`、`electron/kugouApiBridge.cjs`
- `src/services/onlineMusic/{qq,bodian}Provider|Transport`
- 依赖里有 `@neteasecloudmusicapienhanced/api`、`@yakult-green-tea/qq-music-api`、`bodian-music-api`、`kugoumusicapi`

而 LX 上游是**主动移除**内置源的（`1ff6a006 移除所有内置源`）。两边方向正好相反。

**结论：复用 Folia 代码时边界必须卡死。**

| 可以要 | 一个都不能带 |
|---|---|
| `components/visualizer/`（3D 可视化器） | `src/services/onlineMusic/` |
| `components/app/lattice/`（格子歌词） | `electron/*Backend.cjs`、`*ApiBridge.cjs`、`*ApiStartup.cjs` |
| `utils/lyrics/`（歌词解析与渲染提示） | 任何 `*music-api` / `*musicapi` 依赖 |

否则红线会从「树里躺着 411 KB 死代码」升级成**「我们主动引入可运行的音源实现」** ——
性质完全变了，那是我们自己的责任，不再有「上游就是这么带的」这个说法。

## 5. 7.1 入场动画的实现

### 5.1 为什么需要它

启动链路上有一段真实的空窗期：

```
app.whenReady()
  └─ init()                                     ← 可以在这里插东西
       ├─ initAppSetting()   异步，要等数据库初始化（worker dbService.init）
       └─ registerModules()  ← 到这一步才 createWindow()，而窗口是 show: false
            └─ ready-to-show ← 渲染进程就绪后才显示
```

也就是说从「点图标」到「看见界面」之间，要依次等：数据库初始化 → 主窗口创建 → 渲染进程加载。
生产环境是几百毫秒到一两秒，开发环境更久（还要等 webpack dev server 编译）。

### 5.2 为什么是独立窗口，而不是渲染层遮罩

渲染层遮罩（Folia 的做法）不需要额外进程，但它**填不上空窗期的前半段** —— 遮罩本身要等 bundle
加载完才能渲染，而那段空窗正是「bundle 还没加载完」。用独立窗口才能真正盖住整段。

### 5.3 时序：先创建，后刷配置

```
app ready
  ├─ createSplashWindow()      用默认外观立刻显示（此时 global.lx.appSetting 还是 defaultSetting）
  ├─ await initAppSetting()    设置读完
  ├─ applySplashSetting()      把真实外观注入页面；若用户关了开关则立即淡出
  └─ registerModules()         主窗口创建
       └─ ready-to-show
            └─ requestClose()  不足最短时长则等满 → 淡出
```

两个刻意的设计：

- **不等设置读完再显示**。设置读出来之前那几百毫秒正是要填的空窗，等设置的话就白做了。
  代价是首帧只能用默认值，所以 `configQuery()` 会先塞一版（哪怕只是默认值）——
  否则页面会先用白底渲染再变黑，闪一下。
- **外观用 URL query 传入，不走 IPC**。splash 页面不需要 preload、不需要 Node 能力，
  纯静态 HTML + 内联 CSS/JS 就能跑完，攻击面最小。真实配置随后用 `executeJavaScript`
  调用页面的 `window.__overtoneSplashApply(...)` 刷入。

### 5.4 三重保底

| 机制 | 参数 | 防的是什么 |
|---|---|---|
| 最短显示时长 | `common.splashMinMs`（默认 1400ms） | 启动快的机器上一闪而过，观感比没有更差 |
| 兜底上限 | 生产 15s / 开发 60s | 主窗口迟迟不就绪时，alwaysOnTop 的窗口挡住界面让人以为卡死 |
| 开关 | `common.splashEnable` | 用户不想看就关掉 |

开发模式的兜底上限必须放宽：主窗口要等 webpack dev server 编译（本项目约 40~60s），
沿用生产的 15s 会让入场动画提前收掉，看到的是「闪一下然后一片空白」。

### 5.5 可定制项

| 配置键 | 默认 | 说明 |
|---|---|---|
| `common.splashEnable` | `true` | 开关 |
| `common.splashMinMs` | `1400` | 最短显示时长（0.8 / 1.4 / 2 / 3 秒四档） |
| `common.splashImage` | `''` | 自定义启动图，空则用内置声波标识 |
| `common.splashTitle` | `''` | 标题文字，空则显示「泛音」 |

入口在设置页新增的「外观与个性化」分组（`SettingAppearance.vue`），为 7.2 壁纸与 7.3 双档留了位置。

## 6. 踩到的坑

### 6.1 CSS 动画反向写会得到一个纯黑卡片

第一版是 Electron 的常见写法：

```css
.title { opacity: 0; animation: rise 520ms forwards; }
```

这个写法**在所有元素上都依赖动画把内容显示出来**。截图时我看到的是一个纯黑卡片 ——
因为窗口隐藏时不参与合成，动画一帧都没走，元素全部停在 `opacity: 0`。

这不只是截图问题：真实环境里系统禁用动画、或者渲染被节流时，入场动画会退化成一个**黑方块** ——
比没有更难看。改法是把基础状态改成「可见」，动画只负责从 `from` 淡入：

```css
.title { animation: rise 520ms 160ms backwards; }
@keyframes rise { from { opacity: 0; transform: translateY(6px); } }
```

`backwards` 让延迟期间停在 `from`，动画结束后回到元素基础值（可见）。
**动画不推进时最差也是「静态好看」。**

### 6.2 隐藏窗口的 CSS 动画不推进

同一件事的另一面：`win.capturePage()` 在 `show: false` 的窗口上拿不到动画后的画面，
即使 `paintWhenInitiallyHidden` 默认为 true。截图脚本必须先 `showInactive()`。

### 6.3 `destroy()` 掉唯一窗口会触发应用退出

拍第二张图时报 `ERR_FAILED (-2) loading ...`。原因是第一张拍完 `win.destroy()`，
唯一的窗口没了 → 触发 `window-all-closed` → 默认行为是 `app.quit()` → 应用开始退出，
第二个 `loadFile` 自然失败。改成一个窗口来回换参数，并显式接管 `window-all-closed`。

### 6.4 `__dirname` 在 dev 下是可用的（确认过，不是坑）

`splash.html` 是按 `path.join(__dirname, 'splash.html')` 找的，而这是本项目第一个在 dev 下
依赖 `__dirname` 的功能（`winMain` 的 dev 分支走 `http://localhost:9080`，从来没用过它）。

确认结论：`build-config/main/webpack.config.base.js` 里 `target: 'electron-main'`，
webpack 对该 target 下 `node.__dirname` 的默认值就是保留真实值；prod 配置里那两行
`node: { __dirname: false, __filename: false }` 是显式声明同一件事。
`sidecar.cjs` 用同样方式找 `stems_runner.py` 并在 dev 验证通过，是旁证。

前提是别忘了往两个 webpack 配置的 `CopyWebpackPlugin` 里都加拷贝 —— 只加 prod 的话，
dev 里会永远报「找不到 splash.html」，和当初 `stems_runner.py` 是同一个坑。

## 8. 7.2 动态壁纸的实现

### 8.1 做了什么

主题编辑器里的「壁纸」从基本组里的一个缩略图，升级成独立分组：支持**视频**壁纸 +
**模糊**（0–40px）与**遮罩**（0–90%）两个滑块。数据落在三个新的主题键上：

| 键 | 含义 | 默认 |
|---|---|---|
| `--background-video` | 视频壁纸文件名（与 `--background-image` 互斥） | `''` |
| `--background-blur` | 模糊半径，存不带单位的整数字符串 | `'0'` |
| `--background-mask` | 遮罩不透明度百分比 | `'0'` |

17 套内置主题全部带上了这三个默认键（`createThemes.js` → `npm run build:theme` 重新生成
`index.json`）。

### 8.2 为什么需要一个新的图层组件（AppBackground）

`--background-image` 在样式里只有两处消费（`App.vue` 的 `#root`、`PlayDetail` 的 `.bg`），
都走 CSS `background`。CSS 的 background 做不了两件事：

1. **播视频** —— `background-image` 只认图片；
2. **只模糊背景不牵连内容** —— `filter` 会作用到整棵子树。

所以新增 `src/renderer/components/layout/AppBackground/index.vue`：用真实元素
（`<video>` / `<img>`）重画一遍壁纸，模糊与遮罩都加在这一层，内容层完全不受影响。
两个消费点各挂一个实例（`PlayDetail` 传 `behind` 使图层落到 `.bg` 自身背景那一层）。

**兼容性设计：只有「是视频」或「模糊/遮罩 > 0」时才挂载。** 17 套内置主题这三项全是默认值，
因此它们一帧都不会多画——静态图片壁纸（含 GIF）继续走原来的 CSS 路径，行为零变化。

**可见性约定（与图片壁纸一致）**：图层在 `#container` 之下，主题想露出壁纸就得把
`--color-app-background` / `--color-main-background` 设成半透明。这是主题作者的责任，
机制没有额外魔法。

**资源约定**：窗口不可见时（`visibilitychange`）暂停视频——壁纸是常驻的，不暂停会平白
占一路解码；恢复可见时自动续播。

### 8.3 数据流的两个坑

**坑一：TS 会按 JSON 字面量推断 `index.json` 的类型。** 主进程
`import themes from '@common/theme/index.json'` 拿到的是字面量类型（新键被推成 `''`/`'0'`
甚至 `undefined`），往 `extInfo['--background-video']` 赋 `string` 直接报 TS2322。
修法：导入处一次性断言 `const themes = themesJson as LX.Theme[]`，下游全部按 `LX.Theme` 走。

**坑二：老用户主题没有这三个键。** 7.2 之前保存的自定义主题、以及（曾经的）内置主题，
`extInfo['--background-video']` 是 `undefined`。所有读取点都必须按「可能没有」处理：

- `AppBackground`：`getComputedStyle().getPropertyValue()` 天然返回 `''` → 判 `none`；
- 主题编辑器：`syncBgFromExtInfo()` 打开时补默认值再读；
- 主进程 `getTheme()` / 渲染层 `buildThemeColors()`：真值判断后才写 url()。

### 8.4 Electron 的两个平台级坑

**file:// 视频的 autoplay 被拦**。Chromium 把 `file://` 当跨源上下文，连「静音 + autoplay」
都会拦，表现为「`<video>` 挂出来了、`readyState 4`、`muted true`，但一直 paused」；手动
`play()` 反而能成功。修法是主进程显式放开：

```ts
app.commandLine.appendSwitch('autoplay-policy', 'no-user-gesture-required')
```

**Windows 原生窗口遮挡检测**。窗口被别的窗口盖住时 `document.hidden === true`，
AppBackground 会按设计暂停视频。验证脚本如果不在前台跑，测到的 paused 是遮挡导致的
「假故障」——先 `Page.bringToFront` 再测，且判定逻辑要区分「hidden 且 paused」（设计行为）
与「可见却 paused」（真 bug）。

## 9. 7.3 双档外观的实现

### 9.1 做了什么

设置里加了一个 `common.appMode`（`classic` / `personal`），**个性模式**下三件事同时生效：

| # | 行为 | 落点 |
|---|---|---|
| 1 | 侧栏收起成浮层，鼠标移到窗口左边缘滑出 | `App.vue`（`#aside-hotzone` + CSS） |
| 2 | 页面切换带淡入淡出过渡 | `View.vue`（把上游注释掉的 `<transition>` 按模式打开） |
| 3 | 启动时若有在听的歌，直接进播放详情页 | `core/useApp/usePersonalMode.ts` |

**功能一个不少** —— 这不是两套界面，是同一套界面的两种形态。理由在第 3 节已经写过：
真双壳会撞上功能不对称（Folia 的信息架构里没有歌单 / 本地音乐 / 下载 / 设置体系），
而那种「切过去发现少一半功能」反而比只有一套界面更差。

### 9.2 「收起侧栏」比看起来难

难点不在让它变窄，在**不能挤走内容区**。`#container` 是 flex 容器，`#left` 是它的一个
flex item；如果只是把宽度改小（或加 `display: none`），内容区会跟着重排 —— 那不是
「沉浸」，那是「窗口变宽了又抖了一下」。

所以收起靠的是让侧栏**脱离文档流**：

```less
#container.mode-personal {
  #left {
    position: absolute;      // 关键：不再是 flex item，内容区自然铺满
    left: 0; top: 0; bottom: 0;
    z-index: 20;
    transform: translateX(-100%);
    transition: transform @transition-normal, box-shadow @transition-normal;
    background-color: var(--color-main-background);   // 不能用 app-background：它常带 alpha
    backdrop-filter: blur(14px);   // 浮层要有实底，否则文字直接糊在下面的内容上
  }
}
```

**唤出机制**用的是 CSS 而不是 JS 状态：左侧留一条 8px 热区，`:has(#aside-hotzone:hover) #left`
把侧栏推回来；鼠标移到侧栏自己身上后由 `#left:hover` 接管，不会中途收回去。

热区的 `z-index`（19）**特意低于侧栏**（20）—— 这样侧栏展开后，最左边那 8px 不会
被热区吃掉点击；而收起时侧栏整个在视口外，鼠标下最顶层的仍是热区，唤出照样生效。
（用 `:has()` 是因为热区与侧栏是兄弟节点，纯 CSS 没有别的办法表达「hover A 影响 B」。）

### 9.3 动效的落点在 `View.vue` 里本来就留着

`View.vue` 的原始代码长这样：

```html
<router-view v-slot="{ Component }">
  <!-- <transition enter-active-class="animated-fast fadeIn" leave-active-class="animated-fast fadeOut"> -->
  <component :is="Component" class="view-container" />
  <!-- </transition> -->
</router-view>
```

上游把过渡写好又注释掉了。所以「个性模式开启动效」不是新写一套动画，是**按模式决定要不要
包这层 `<transition>`** —— 复用现成的 `animated-fast fadeIn/fadeOut`（`animate.less` 里已有，
0.3s）。

经典模式保持原样（不包），不改变已经用惯的人的观感。**两档的差别要落在明处**，
而不是到处都动一下。

### 9.4 顺手修掉的一个旧缺陷

查 i18n 时发现主题列表里显示的是字面量 `theme_overtone`。根因在 `SettingBasic.vue`：

```js
return defaultThemesRaw.map(theme => ({ ...theme, isDefault: true, name: t('theme_' + theme.id) }))
```

它对所有内置主题都走 `t('theme_' + id)` 取名，而品牌化把 id 改成 `overtone` /
`overtone_dark` 时没同步语言文件，于是 `t()` 找不到键、原样返回键名。补上 4 个语言的
`theme_overtone` / `theme_overtone_dark` 即修复（另外 15 套主题的键本来就在）。

### 9.5 验证方式

`build-config/drive-mode.js`，五步：读回设置面板 → 切个性模式量几何 → 派发真实鼠标
事件到左边缘看侧栏滑不滑出 → 重载后设当前歌曲看是否自动进播放页 → 切回经典模式看复原。

为什么必须量真实 `rect` 而不是看编译结果：收放全靠 `position: absolute` + `transform`，
少一个 `position: absolute`，「收起」就会静默变成「内容区被挤走一半」，而编译期一路绿灯。

两个细节：`:hover` / `:has()` 必须用 `Input.dispatchMouseEvent` 派发真实输入事件才触发，
直接改 class 测不到；「自动进播放页」的起点必须是干净的（重载后 `musicInfo.id` 为空），
否则测不出是 watch 生效还是本来就开着。

## 10. 7.4 跟随封面取色

### 10.1 做了什么

设置 → 外观里多了一个开关 `common.coverColor`（**默认关**）。打开之后：

| # | 行为 | 落点 |
|---|---|---|
| 1 | 从当前歌曲封面提主色，写成全局变量 `--cover-color` | `core/useApp/useCoverColor.ts` |
| 2 | 背景层多一层**主色染色**（上浓下淡的渐变） | `AppBackground/.tint` |
| 3 | 壁纸**遮罩的颜色**从「主题底色」换成「这首歌的颜色」 | `AppBackground/.mask` |

第 3 条是这个功能最直接的形态：同一个遮罩不透明度，压下去的不再是白或黑，而是封面那个颜色。

默认关的理由：它带来明显的视觉变化，而且**依赖主题背景是半透明的**才看得出来（见 10.6），
不适合升级后一睁眼界面就变了个样。

### 10.2 读图这一步必须留在主进程

渲染层要算颜色，唯一的路是把图画进 `<canvas>` 再 `getImageData` —— 而 canvas 一旦被
「非同一来源」的图污染，`getImageData` 直接抛 `SecurityError`。封面的三种来源里两种会踩雷：

- **本地文件路径**：`getMusicFilePic` 对超过 400KB 的封面会落到临时文件上，`file://` 是不透明源；
- **在线歌曲的 http 地址**：服务端基本不会给 CORS 头。

`nativeImage` 读图不受这些约束，所以由它把图读出来、缩到 36×36、编码成 PNG data URL 交回渲染层
（`src/main/modules/coverColor/`）。data URL 那条路不用绕 IPC —— 它本身已经是解码结果，几百 KB
的字符串在 IPC 上是要老实复制一遍的。

### 10.3 但量化故意留在渲染层

`nativeImage.toBitmap()` 返回缓冲区的通道顺序（BGRA / RGBA）在不同平台与版本上是有歧义的，
拿它算颜色等于赌运气。而 `<canvas>` 的 `getImageData` 保证是 RGBA —— 让渲染层算，这个坑天然不存在。

代价是取色要跨两条链路（渲染层 → 主进程读图 → 渲染层量化），换来的是「不会算错颜色」。

### 10.4 取色算法：色相分桶，不做平均色

平均色是错的方向：封面上的背景、留白、文字会把平均色糊成一片灰，那恰恰是封面**最没信息量**的颜色。

实际做法是按色相分 12 个桶，用 `s²·v` 做权重累加 —— 「又鲜艳又明亮」的像素说话最大声，
最后取分量最重的那个桶的加权平均。这是「一眼看过去这封面是什么颜色」的算法近似。

两条硬规则：

- **灰度封面不染色**。一个像素都没进桶 = 这张封面是黑白的，灰度图没有色相可言，
  硬提饱和度只会凭空捏造一个颜色出来 → 返回 `null`，变量被撤掉。
- **只动饱和度和明度，色相原封不动**。饱和度托底（≥0.35，封面常有大片灰调，不提上来染色层毫无存在感）、
  明度夹在中间段（0.32 ~ 0.8，太暗在深色主题里等于没染，太亮会把壁纸洗白）。
  色相才是「这首歌的味道」，动了就不是跟随了。

### 10.5 变量写在 `documentElement` 的内联样式上

不能写进 `setTheme` 用的那个 `<style>`：那个元素每次切主题都会被整段重写，`--cover-color` 会被冲掉。
内联样式的优先级天然高于任何选择器规则，主题怎么切都盖不掉。

关闭开关或没有封面时是 `removeProperty`，**不是写一个兜底色** —— 消费端全都写成
`var(--cover-color, 原有的颜色)`，变量不存在即等于「没这个功能」。
`AppBackground` 的 `state.tint` 也是靠「这个变量在不在」判断的，不必再去读一遍配置。

代价是 `AppBackground` 要多盯一眼 `<html>` 的 `style` 属性变化（它原本只盯主题那个 `<style>` 元素），
否则切歌时这一层不会重读。

### 10.6 ⚠️ 必须说清的限制：看不看得见，取决于主题

染色层和遮罩都在**背景层**，所以它们透不透得出来，取决于上层内容有多不透明：

| 位置 | 挡在中间的东西 | 默认主题（余音绕梁 / 摸鱼绿）实测 |
|---|---|---|
| 主界面 | `#container` 的 `--color-main-background` | `rgba(255,255,255,1)` —— 不透明，只有标题栏那条带 alpha 的 `--color-app-background` 能透出来 |
| 播放详情页 | `.bg::after` 的 `--color-main-background` | `rgb(255,255,255)` —— 实测中部像素 `(254,254,254)`，截图就是一张白纸 |

**这不是缺陷，是上游刻意的：内容不透明时背景就不该透出来。** 壁纸功能同理 ——
这也是为什么「壁纸能看见」的前提一直是「主题把背景设成半透明」。

所以这个开关的实际效果 = **主题背景的透明度 × 染色强度**。想让它在自己的主题里明显起来，
要么把主题的 `--color-main-background` 调成半透明，要么把壁纸的遮罩调上去。

### 10.7 验证方式

`build-config/drive-cover-color.js`，七步：

1. 开关关闭 → 不该有任何染色（功能不能偷偷生效）；
2. **已知主色**的封面（`#2f6fd0`）→ 取到的颜色必须落在那个色相上（「出来一个值」不算数）；
3. 换成绿色封面 → 颜色要跟着变（不然就是取了一次就锁死）；
4. 黑白封面 → 不该染色；
5. **本地文件路径**的封面 → 走主进程 `nativeImage` 那条路也要能取色（和 data URL 是两条完全不同的读图链路，只测一条等于没测）；
6. 关掉开关 → 变量与染色层都要消失；
7. 播放详情页 + 真实壁纸 → 染色层与遮罩都要跟着封面色走。

判定用**色相**而不是「等于某个 hex」：取色走的是量化 + 氛围化，结果本来就不是原图那个像素值，
但对色相是忠实的。拿原值比会永远对不上，拿色相比才能同时验证「提取得对」和「没乱改色相」。

第 7 步的留档图需要额外处理一下：`.bg::after` 那块不透明白蒙版会把背景层整个盖住，
静态截图只会是白纸。所以截图前把这块蒙版临时改成透明，**等价于「用户用了主背景半透明的主题」** ——
这是唯一能让静态截图说清这个功能的办法，跑完立刻撤掉。

实测结果：

```
✓ 蓝色封面 → #2e6dcc（色相差 0.1°）    ✓ 绿色封面 → #3aa76d（色相差 0.0°）
✓ 灰度封面 → 不染色                    ✓ 本地文件路径 → #cc432e（色相差 0.1°）
✓ 播放详情页遮罩色 = rgb(204,67,46)（色相差 0.1°）
```

## 11. 7.5 通透主题（让壁纸与取色真正看得见）

### 11.1 问题的确切形状

10.6 记下了那个限制，但当时只当成「已知限制」。它其实是**功能缺陷**：默认主题下
7.2 的动态壁纸和 7.4 的封面取色**完全没有效果**，用户设了壁纸也看不见。

把链条拆开，挡路的东西只有一个：

| 位置 | 谁在上面 | 默认主题（余音绕梁）的取值 |
|---|---|---|
| 主界面 | `#container` 的 `--color-app-background` | `var(--color-primary-light-600-alpha-700)` → **alpha 0.3**（**能透**） |
| 播放详情页 | `.bg::after` 的 `--color-main-background` | `rgba(255, 255, 255, 1)`（**全挡**） |

两个背景色不是一回事，别混：

- **`--color-app-background`** 是内容层**之下**的「染色底」（最外层容器），
  默认主题本来就给它 0.3 —— 所以主界面上壁纸其实是能透一点的。
- **`--color-main-background`** 是**内容面板**（卡片、列表，以及播放详情页那层蒙版），
  默认主题给的是不透明白。**播放详情页的壁纸 100% 被它挡掉**。

顺带记一笔反直觉的地方：`--color-primary-light-600-alpha-700` 里的 `700` **不是**
alpha 0.7。`RGB_Alpha_Shade(p, c)` 在 `p > 0` 时取的是 `1 - p`，所以 `alpha-700`
其实是 **0.3**，`alpha-300` 才是 0.7。想当然地去读那个数字会读反。

### 11.2 为什么是「加一套主题」而不是「改默认主题」

改默认主题看起来更彻底，但它会**替所有人做决定**：不透明的内容背景是有道理的
（保证文字对比度），把它改成 0.62 会让每个用户的界面都变「飘」，而且不可逆。

所以走「加一套 + 给一个动作」：

1. 内置一对开箱即用的通透主题，切过去就有效果；
2. 主题编辑器里给一个一步到位的开关，让任意主题都能被调透（见 11.4）。

### 11.3 两套通透主题

| id | 名字 | 内容层 | 容器底色 | 模糊 / 遮罩 |
|---|---|---|---|---|
| `overtone_glass` | 澄澈泛音 | `rgba(255,255,255,0.62)` | `rgba(255,255,255,0.35)` | 14 / 16 |
| `overtone_glass_dark` | 澄澈夜色 | `rgba(19,19,19,0.72)` | `rgba(0,0,0,0.25)` | 14 / 16 |

主色沿用品牌靛紫（深色版用亮靛蓝），所以**换主题不会换掉品牌色**，变的只是透明度。

两个背景刻意用**中性黑白**而不是像默认主题那样从主色派生
（`var(--color-primary-light-600-alpha-*)`）：

> 主色会稀释封面取色的色相。通透主题存在的意义正是**让歌的颜色当主角**，
> 再叠一层主题色等于自己跟自己抢。

默认带 14 的模糊也是这个思路：半透明的内容层上，文字需要和壁纸的细节脱开一点，
否则歌词压在复杂壁纸上会读不清。

### 11.4 「一键通透」这个按钮

`--color-main-background` 的 alpha **本来就能调** —— 基本设置里那个「内容区域背景颜色」
的取色器带 alpha 通道，预设里甚至就有 `rgba(25.82, 23.65, 46.6, 0.54)` 这种半透明值。

问题是**没人会去那里找它**：那个控件看起来是「选颜色」的，不像「调透明度」的，
而且它离壁纸设置隔着一整个分组。所以真正缺的不是能力，是**一个明确的一步到位**。

做法是在主题编辑器的**壁纸分组**里加一个按钮（放这里而不是颜色分组，因为它服务于壁纸）：

- 未通透 → 显示「一键通透」，点了把 alpha 调到 0.62（深色 0.72）；
- 已通透 → 显示「恢复不透明」，点了把 alpha 调回 1；
- **只动 alpha、保留 RGB** —— 用户挑的颜色不该被这个动作改掉；
- 改完顺手 `setMainBgColor()` 推给基本组那个取色器，否则两个控件会各说各话。

按钮状态由一个 `isTranslucent` ref 撑着，它同时挂在两个地方更新：主题载入时算一次，
以及取色器每次变化时重算（用户也可能直接在取色器里拖 alpha，按钮上的字得跟着变）。

深色档取 0.72 而不是 0.62：深色下内容层本来就更沉，用浅色那档会糊得读不清。

### 11.5 验证方式

`build-config/drive-glass.js`，六步。判定**用像素，不用「读一下 CSS 变量对不对」**：

> 变量对 ≠ 看得见。这个功能的坑恰恰是「变量全对，但被上层一块不透明的底盖住了」，
> 只读变量会得出「一切正常」的错误结论。

脚本自带一个最小 PNG 解码（Node 内置 `zlib` + 四种反滤波，约 50 行），
把截图解成像素直接量**红度**（`r - g`）—— 为采样一次装 Pillow / sharp 不划算。

关键一步是「同一张壁纸，两个主题下比」：

```
通透主题 + 红壁纸：中部平均 rgb(248, 228, 225)  红度 20
不透明主题 + 红壁纸：中部平均 rgb(255, 255, 255)  红度  0
```

同一张图、同一个位置，差别是量出来的，不是推出来的。

留档图 `notes/preview/splash/22`~`25`：`22-glass-theme-setting`（主题列表里的两套通透主题）、
`23-glass-wallpaper`（通透主题 + 红壁纸）、`24-opaque-wallpaper`（**同一张红壁纸** + 不透明主题）、
`25-theme-editor-translucent`（编辑器里的「恢复不透明」按钮，实线主色 = 当前已通透）。

> 编号从 22 起是因为阶段 6 已经用掉了 14~18 —— 一开始和 `18-playdetail-ai-lyric` 撞了号，
> 趁着写日志一并纠正并把脚本里的文件名同步了（避免下次跑又生成旧名）。

### 11.6 这轮踩到的一个新坑：dev 的编译错误 overlay

跑第一遍时六步挂了 12 项，三张截图中部平均色都是 `rgb(52, 32, 35)` 这种暗色 ——
一度读成「深色壁纸生效了」。**实际是 webpack-dev-server 弹了全屏的 eslint error overlay**
（两处 `|| []` 触发了 `prefer-nullish-coalescing`），把整个界面盖住了。

这个 overlay 特别容易骗人，因为：

- 它盖住界面后截图是**暗的**，而暗色很像「深色主题 / 深色壁纸生效」；
- dev 的编译日志看着是正常的，`build:renderer` 也可能过（两套独立编译）；
- 它只在 dev 下出现，所以「生产构建没问题」不能作为它不存在的证据。

现在脚本起点会显式检查 `#webpack-dev-server-client-overlay`，有就直接报错退出 ——
把「截图全废」这个隐性问题变成显式失败。
