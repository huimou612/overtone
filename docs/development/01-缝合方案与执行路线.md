## 2. 路线判定：为什么走源码合并而不是逆向

**逆向**（Ghidra / JADX / REA）解决的是「拿不到源码时如何理解程序」。

在这两个目标上它全部失效，因为源码就在手边：

- Folia 的 `package.json` 里 `license` 字段直接写了 AGPL-3.0，`repository` 指向公开仓库
- LX Music 安装包的 asar 里就是 webpack 打包产物，对应的源码在 GitHub 上
- 拿到源码后你能看到**注释、提交历史、issue 讨论、README** —— 信息量是逆向伪代码的一百倍

**所以路线是：`git clone` 两个仓库 → 在本地做合并开发 → 推送到自己的 GitHub。**

REA 在这个项目里的正确用法（保留，但降级为辅）：
1. 核对「你机器上跑的发行版」与「GitHub 上的源码」是否一致（防止被塞私货）
2. 检查某个模块有没有未开源的私有依赖
3. 以后如果遇到闭源目标（比如某个国产付费软件），再切回逆向模式

## 3. 许可证与法律边界（这一节请务必读完）

### 3.1 许可证兼容性判断

| 组件 | 许可证 | 性质 |
|---|---|---|
| LX Music | Apache-2.0 | 宽松。可改、可商用、可闭源分发（需保留版权与变更声明） |
| Folia | **AGPL-3.0** | **强传染**。修改或通过网络提供服务，都必须以 AGPL-3.0 公开全部源码 |

**兼容结论：可以合并。** Apache-2.0 的代码可以并入 AGPL-3.0 项目（Apache 官方明确允许）。反过来不行。

**因此你的新项目必须是：**
- 整体许可证：**AGPL-3.0**
- 保留 `LICENSE`（AGPL-3.0 全文）
- 保留双方版权声明（LX 的 Apache-2.0 声明 + Folia 的 AGPL 声明）
- 在 README 里明确标注「基于 lyswhut/lx-music-desktop 与 chthollyphile/folia-major 二次开发」
- 任何修改过的文件要标注「已修改」
- **如果你将来给它加服务端（同步 / 云库），服务端也必须开源**

好消息：你的计划是「上传到 GitHub」，这恰好满足 AGPL 的开源义务。**没有冲突。**

### 3.2 真正的法律风险：在线音源（红线）

这是比许可证重要得多的问题。

两个项目都属于「音源聚合」类软件，但**它们的官方仓库都不含音源接口**：

- LX Music 的做法：主程序里只有 `import_user_api` / `set_user_api` / `request_user_api` 这套机制，**音源脚本由用户自行导入**，作者不提供
- Folia 的 `electron/` 里有 `neteaseBackend.cjs`、`qqBackend.cjs`、`kugouApiBridge.cjs`、`bodianApiBridge.cjs` —— 这部分是它自己接的第三方平台

**这类接口的实质是绕过平台授权获取受版权保护的内容。** 在中国大陆属于侵权风险区，在 GitHub 上会收到 DMCA 下架通知（LX Music 历史上就经历过仓库风波）。

**本方案的处置原则：**

| 处置 | 内容 |
|---|---|
| ❌ 禁止 | 把 Folia 的 `neteaseBackend` / `qqBackend` / `kugouApiBridge` / `bodianApiBridge` / `src/services/onlineMusic` 搬进新项目并内置 |
| ✅ 允许 | 保留 LX 原有的「用户自行导入音源」机制（责任转移给用户，与 LX 官方做法一致） |
| ✅ 允许 | 本地音乐库、Navidrome / 自建音乐服务器、用户自有文件的播放 |
| ✅ 主打 | **AI 能力**（音源分离、AI 歌词）—— 这才是技术壁垒，且完全无版权风险 |

这个取舍不是妥协，而是**让项目能长期活着**。AI 音源分离 + AI 歌词处理的技术含量，远高于再接一个平台音源。

## 4. 架构设计：怎么缝

### 4.1 先看清两个项目的结构

**LX Music（外壳）—— webpack 四入口构建**

```
build-config/          ← 4 套 webpack 配置
  main/                  主进程
  renderer/              主 UI 窗口（Vue 3）
  renderer-lyric/        桌面歌词独立窗口（Vue 3）
  renderer-scripts/      注入脚本
src/
  main/        (144)   ← 主进程：modules 94 / worker 27 / utils 7
  renderer/    (444)   ← UI：views 97 / components 71 / core 45 / store 36 / utils 112
  renderer-lyric/(35)  ← 桌面歌词窗口
  common/      (78)    ← 共享层：ipcNames.ts（IPC 契约）★缝合入口
```

**Folia（能力）—— 主进程侧才是可搬的部分**

```

  neteaseBackend.cjs ⛔ 音源（红线）
  qqBackend.cjs      ⛔ 音源（红线）
  kugouApiBridge.cjs ⛔ 音源（红线）
  bodianApiBridge.cjs⛔ 音源（红线）
  wallpaper*.cjs     壁纸功能
src/
  components/ (906)  ⚠ React 组件，与 Vue 不兼容，不能直接搬
  library/suites(196)⚠ React 生态

  workers/ (3)       lyricsParser / metadataParser / automixAnalysis（算法思想可参考）
```

### 4.2 缝合的技术路径

**核心洞察：Folia 真正值钱的东西在主进程，而主进程的代码（`.cjs`）与前端框架无关。**

这意味着缝合的接口点非常干净：

```
┌──────────────────────────────────────────────────────┐
│  LX Music 外壳（Vue 3 + Electron 主进程）              │
│                                                      │
│  src/renderer/views/  ← 新增 Vue 页面（你自己写）      │
│         │                                            │
│         │  调用 IPC（src/common/ipcNames.ts）         │
│         ▼                                            │
│  src/main/modules/    ← 新增主进程模块                 │
│         │                                            │
│         │  载入（CommonJS，语言无关）                  │
│         ▼                                            │
│  ┌────────────────────────────────────────────┐      │
│  │ Folia 能力层（从 electron/ 搬过来）          │      │
│  │  • analysis/  → HTDemucs 音源分离           │      │
│  │  • aiTextClient → AI 歌词处理               │      │
│  │  • transcode/ → 音频转码                    │      │
│  │  • modSystem/ → 插件系统                    │      │
│  └────────────────────────────────────────────┘      │
└──────────────────────────────────────────────────────┘
```

**加一个新能力的标准动作（三步）：**

1. `src/common/ipcNames.ts` —— 新增一个模块，例如：
   ```ts
   ai: {
     separate_stems: 'separate_stems',      // 音源分离
     separate_progress: 'separate_progress',
     generate_lyric: 'generate_lyric',      // AI 歌词
     get_models: 'get_models',
   }
   ```
   命名规则是 `${模块名}_${事件名}`，会自动拼成 `ai_separate_stems`。

2. `src/main/modules/` —— 新增 `ai.ts`（或 `ai/` 目录），把 Folia 的 `.cjs` 能力包一层，注册 IPC 处理器。

3. `src/renderer/views/` —— 新增 Vue 页面 + 在 `router.ts` 挂路由，调用 `ipc.ai_separate_stems(...)`。

**LX Music 现成的可复用骨架（省很多事）：**

| 已有能力 | 用途 |
|---|---|
| `winMain_import_user_api` / `get_user_api_list` / `request_user_api` | 音源扩展机制（责任转移给用户） |
| `winMain_get_lyric_raw` / `save_lyric_edited` | 歌词读取与人工编辑，AI 歌词改完可直接写入 |
| `winMain_get_sound_effect_eq_preset` / `convolution_preset` | 音效系统，可挂接音源分离的输出 |
| `winMain_get_data` / `save_data` | 通用 KV 存储，AI 密钥可存这里 |
| `winMain_sync_action` / `sync_get_server_devices` | 同步机制骨架 |
| `src/main/worker`（27 个） | 已有 worker 进程管理范式，AI 推理可复用 |

### 4.3 实际落地的形态（与上面这张流程图的偏差）

上面那张图里有一层写着「`src/renderer/views/` ← 新增 Vue 页面 + 挂路由」。
**这一层实际上没有被执行。**

阶段 3 与阶段 4 收尾时，两个能力都做成了**对话框组件**，挂在既有的歌词右键菜单上：

```
原计划                              实际做的
─────────────────────────────       ─────────────────────────────
新增 Vue 页面 + router.ts 挂路由     新增大两个 Modal 组件
侧栏出现一级入口                     挂在 LyricMenu 的右键菜单里
「打开泛音就能看到这软件多了什么」   「要先播放一首歌、进播放详情、右键歌词」
```

省事、破坏性小、不用碰路由与侧栏，这在「先把链路打通」阶段是对的取舍。
代价是**差异化不可见** —— 用外面看它仍然是一台换了皮肤的 LX。

这不是代码缺陷，是信息架构的欠账。已作为**阶段 6** 补进计划（见第 7 节），
详细的能力清单与入口位置见 `05-能力地图.md`。

## 6. 三种缝合形态（需要你选一个）

### 方案 A：LX 外壳 + Folia 能力层（推荐）

- **外壳**：LX Music 的 Vue 3 界面、播放器、音乐库、桌面歌词窗口
- **能力**：移植 Folia 的主进程 AI 能力（音源分离 / AI 歌词 / 插件系统 / 转码）
- **UI 策略**：新功能页面用 Vue 自己写，视觉上参考 Folia
- **工程量**：中。核心工作量在 ① 主进程能力接入 ② 新页面用 Vue 写
- **优点**：符合你的原始描述；LX 的音乐库管理和播放稳定性成熟；AGPL 合规清晰
- **缺点**：**拿不到 Folia 最出名的「绚丽歌词动画」**（那部分在 React 里，需重写）

### 方案 B：Folia 外壳 + LX 音乐库能力（反方向）

- **外壳**：Folia 的 React UI（保留它最值钱的视觉卖点）
- **能力**：移植 LX Music 的音乐库管理、列表、下载、桌面歌词窗口
- **工程量**：中偏大。LX 的 444 个 renderer 文件要挑着搬进 React
- **优点**：保留 Folia 的视觉差异化和市场辨识度
- **缺点**：与你的原话「用第二个软件的外壳」相反；LX 的桌面歌词窗口是 Vue，要重写

### 方案 C：双入口并存（最快出东西）

- 两个独立 Electron 应用打包在一起，用一个启动器切换
- **工程量**：小。几天内能有可运行的产物
- **优点**：最快看到成果，两边的完整性都不破坏
- **缺点**：体验割裂，本质是两个软件放一起，谈不上「缝合」
- **适合**：先出个 demo 验证方向，再决定往 A 还是 B 演进

> **我的建议**：如果你的核心诉求是「造一个真正属于自己的软件」，选 **A**。
> 如果你想尽快有一个能发出去的东西，选 **C** 过渡，然后往 A 收敛。
> 方案 B 只有在你非常看重 Folia 那套歌词动画视觉时才值得选。

### 阶段 4：接入音源分离（重头戏）

- [x] 搬 `electron/analysis/*`

- [x] 准备 Python 运行时（sidecar）

**实际落地的形态与开工时的设想有两处不同，都不是选择而是被事实推着走：**

1. **推理没有走 onnxruntime-node。** 走了 Python sidecar（应用自带一份 36 MB 的
   Python 运行时，随模型一起下载）。原因只有一个：`enable_mem_reuse` 与
   `enable_cpu_mem_arena` 这两个内存开关**只有 Python 绑定能设**，关掉它们能把峰值
   内存从 ~2.5 GB 压到 ~500 MB（实测 543 MB）。onnxruntime-node 的 `extra` 选项只对
   WASM 后端生效，C API 也没暴露这两个开关。不换的话 4 分钟的歌会吃掉几 GB。
2. **`other` 这一轨必须自己留下。** 上游 runner 只回传 drums/bass/vocals 三条轨，
   「伴奏」需要 `drums+bass+other`。所以这一版改成了**双桶累加**：人声一桶、
   其余三源之和一桶，整曲缓冲直接减半（4 分钟的歌省约 170 MB），结果与逐位相加等价。

另外两个为了「能跑完整首歌」而做的调整：

- **回传方式改成 Python 直接写 WAV。** 上游走 IPC 回传三条裸 float32 轨，整曲就是
  254 MB 白搬一趟；现在 Python 自己写盘，主进程只拿路径。
- **解码放在渲染进程。** Chromium 的 Web Audio 能解 mp3/flac/m4a/wav，Node 侧一个都
  不能。渲染层解出 PCM 后**自己写 `mix.in`**（85 MB 不走 IPC），主进程只收「路径 +
  采样数」，并用字节数核对完整性。

> 完成时间：2026-10-13。
>
> **内核验证**（`build-config/probe-stems.py`，用真素材按固定比例混音，与「错配对」比较）：
> 140 秒版本 `vocals↔voice = 0.9954`、`accomp↔bgm = 0.9903`，错配 `0.0134 / 0.0132`；
> 峰值工作集 601.3 MB，推理 88.23 s / 90.9 s 墙钟 = 1.54× 实时。
>
> **界面端到端验证**（`build-config/drive-stems-local.js --run`，本地音频走完整条链路）：
> 90 秒音频，点击到出文件 56.5 s，其中推理 51.67 s（**1.74× 实时**），峰值内存 543.2 MB；

> **人声↔源人声 0.9983**（错配 0.0334）、**伴奏↔源伴奏 0.9746**（错配 0.0254），
> 两条产物各 89.9 秒、非静音，`VERDICT: PASS`。
> 渲染进程零 error。
>
